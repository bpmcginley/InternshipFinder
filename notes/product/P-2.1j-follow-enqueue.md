## Transaction and immutable identity

`enqueueFollowSnapshot` accepts a subscriber ID, trusted public snapshot bytes, catalog, explicit matcher limits, authoritative `upperBound`, `maxProgressBytes` and `maxPendingBytes`. The pending budget is a positive safe integer no greater than the existing 32-KiB outbox storage ceiling; no send-volume default is chosen. The helper owns a byte copy and a numeric clock sample before awaits, reads bounded validated confirmed progress and invokes the inherited matcher internally. It never accepts caller-built matches or pending metadata. The exact public bytes are SHA-256 hashed; their validated generated date and hash are pinned, without retaining public role facts, addresses, tokens or rendered mail.

One D1 batch requires every captured confirmed scope to retain its scope key, confirmation timestamp, generation and `from` watermark, and rejects any additional confirmed scope. The count stops at captured count plus one; a partial confirmed-scope index avoids scanning unrelated pending scopes. Only a matching full set can create the immutable daily outbox and its pending metadata. An active unexpired queued/leased/attempting job for the subscriber blocks a new job, including across UTC days. This prevents overlapping snapshots while prior matched watermarks remain uncommitted. Same-day exact retries return the existing ID only if payload, public digest/date, captured metadata, current scopes and job state/expiry still match. Changed snapshots, old-API jobs lacking pinned metadata, stale scopes or terminal jobs return `conflict`; they are never adopted or overwritten.

Pending JSON has exactly `{scopeKey, generation, confirmedAt, from, to}` per confirmed scope, with validated canonical keys/instants, current server identities and `to` equal to the authoritative snapshot date. The helper bounds the complete encoded JSON before the write, and the schema enforces its array and byte ceiling. Matched references reuse the existing outbox validator. No permanent watermark is advanced by enqueueing. A failure inserting pending data rolls back the outbox insertion too; an ambiguous response after commit can be retried against the identical immutable identity.

## Lifetime and deferred integration

`follow_pending_progress` references one outbox job with cascading deletion; an update trigger prohibits changing its pinned data. Existing cancellation, expiry, acceptance and uncertainty transitions erase pending metadata in the same statement. Deleting a confirmed scope cancels the aggregate and removes pending data while surviving durable watermarks remain unchanged; a next-day scan can recover those matches. Full subscriber/job deletion cascades. The existing keyed actual-attempt-day HMAC marker remains independent and unchanged.

Authorization remains the existing 48-hour job window, and existing cleanup cancels expired jobs and removes job rows after seven days. The same cleanup invocation is required to physically erase expired pending data; no new timer, retention period or historical table is introduced. Cancellation does not rebuild the immutable same-day job. Accepted/uncertain terminal progress finalization is deliberately absent: a future integrated dispatcher must finalize progress atomically under the pending identity before enabling sending. Existing terminal helpers are unchanged apart from automatic metadata erasure; this dormant slice does not claim end-to-end duplicate-free delivery or transport fencing. Public snapshot production, immutable retrieval, completeness/authenticity, recovery/freshness choices and all provider/deployment gates remain separate.
