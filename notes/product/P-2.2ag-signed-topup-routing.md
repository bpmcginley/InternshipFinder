## Classification and historical terms

The dedicated existing `STRIPE_PRICE_TOPUP` and Stripe key configure historical recovery. The webhook additionally requires its existing signing secret. This works without subscription/listing offers and when current top-up/payment sales switches are off. Operators must retain the historical configuration after accepting purchases. No configuration means unrelated billing events take their original path without added top-up queries or provider requests. Explicitly marked supported top-up events cannot fall through even if recovery configuration is absent.

Checkout hints use #363's stored-attempt and mode-separated fingerprint association. Reversal hints use #364's payment fingerprint lookup. A known terminal fingerprint is acknowledged without resurrecting erased credit. Supported ambiguous events return the existing generic retry error, which removes the existing receipt. Confirmed typed outcomes retain it. Explicitly marked unsupported families are acknowledged as ignored inside this boundary without financial mutation. Event totals/status and browser redirects never grant credit.

The historical resolver uses the configured Price and existing approved `topup-v1`, USD 300 minor units, 25-run terms. It passes the signed mode to the already-bounded authoritative Checkout/payment readers, which verify the exact stored association, Price, mode and immutable economics. No separate Price GET or current active-Price requirement is introduced. An unknown version, wrong Price/mode or ambiguous provider result remains retryable.

Stripe documents nullable PaymentIntent references on [refunds](https://docs.stripe.com/api/refunds/object), [disputes](https://docs.stripe.com/api/disputes/object) and [Charges](https://docs.stripe.com/api/charges/object). Missing event PI therefore does not establish a legacy payment. A bounded authoritative Charge GET verifies exact identity/mode and resolves it. After an unclassified typed lookup, a durable employer payment match skips further discovery. Otherwise one bounded PI GET checks metadata and any known attempt hint. Positive top-up association stays retryable, including reversal-before-first-grant. A verified non-top-up legacy Charge with no PI can return to the unchanged legacy path. Missing/malformed/failed discovery does not authorize fallthrough. Account/context-scoped inputs are not silently resolved against the platform key.

Discovery performs at most two GETs, each using the existing pinned Stripe adapter's ten-second absolute deadline, abort, 256-KiB streamed response cap, manual redirect rejection and anonymous error boundary. There are no retries, arbitrary paths, customer discovery or copied provider payloads. Ordinary configured legacy flows may require this extra classification when their association is otherwise unknown. Actual financial recovery retains its existing independent bounded readers and revision/CAS semantics.
