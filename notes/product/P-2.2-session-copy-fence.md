# P-2.2 prerequisite: session-copy deletion fence

[PR #297](https://github.com/bpmcginley/InternshipFinder/pull/297), independently based on main d003e287. **Needs Bruce for Worker merge/deployment.** No top-up stack is imported, no production deployment occurred, and no new schema or retention is introduced.

Previously, copySession authenticated a source before its write transaction. Deleting/signing out that source between the read and write still allowed a new live session. A synthetic local reproduction confirmed this behavior; no actual account or provider was used.

The copy transaction now conditionally inserts the new session only if the exact source hash, account, tier/provider and unexpired row still match. It consumes the existing unique copy capability in the same batch, then trims old sessions only when the preceding insert changed one row. Deletion/sign-out/expiry between preflight and the write produces the existing401 auth response, no new session/copy record, and no unrelated trimming. A concurrent duplicate capability fails its uniqueness constraint and rolls the new session back with the existing409 copied response.

Direct createSession runtime behavior, token hashing/randomness, sliding lifetime,20-session limit, one-use/no-copy-of-copy policy, independent sign-out, successful response keys/values, routes and visible strings remain unchanged. Existing legacy ID-token sign-in remains supported. This fixes the copy race only; a fresh provider sign-in may create a new session, and future payment reservation/deletion must still share their own transaction fence. No claim is made that this alone completes top-up deletion, admission retry/idempotency or activation.
