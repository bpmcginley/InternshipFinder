## Invariant and dispatch boundary

Only a durable `attempting` job transitioning to `accepted` or `uncertain` can consume its captured snapshot window. The new BEFORE-state trigger advances a surviving scope only when its scope key, server generation, original confirmation timestamp and current `from` watermark still match the validated pending row. It writes the pinned `to`, never regresses progress, and never recreates deleted scopes. Existing AFTER-state erasure then removes pending metadata in the same statement. Accepted last-send metadata, state, progress and erasure remain one atomic transaction; a failure rolls all of them back.

The new `beginFollowSnapshotAttempt` entry requires a valid pending row, the exact current confirmed-scope set and matching progress before it inserts the existing actual-attempt-day HMAC marker. A missing/invalid row, new scope, changed lifetime/watermark or future snapshot fails closed and uses pre-attempt cancellation without taking a marker or advancing anything. An old queued snapshot can become stale when cleanup finalizes a prior expired attempt; it cannot later claim a marker and replay that captured window. No provider is called by this entry point.

The existing `beginFollowDigestAttempt` remains compatible for standalone dormant jobs without pending metadata. It still validates a pending row when one is present. A future snapshot dispatcher must use the strict entry, never the legacy fallback. The keyed marker, lease rules and standalone queue tests remain unchanged. The inherited enqueue lifecycle test now expects uncertain snapshot progress consumption and uses genuinely later synthetic first-seen values for its next snapshot.

## Deletion, invalid metadata and retention

Pre-attempt cancellation advances nothing. Deleting a confirmed scope from an attempted snapshot changes that job to uncertain, finalizes only unchanged surviving captured scopes and erases pending data atomically. Removed/recreated scopes cannot inherit the previous generation's progress. Full subscriber deletion cascades all user-linked scope/job/pending rows, while the separately keyed daily marker retains its original expiry. Standalone jobs without snapshot metadata retain their prior cancellation behavior.

`follow_valid_pending` is a validation view, not retained data. One job-key lookup validates the existing 32-KiB JSON array, exact field set/types, unique scope keys, generation shape, canonical UTC instants, ordered confirmation/from/to, and pinned snapshot date/digest shape. The finalizer uses bounded captured-key lookups; the attempt guard uses current scope/progress indexes and stops when an extra confirmed scope appears. Actual local D1 query-plan evidence confirms the pending validation starts with a job-key index lookup rather than a table scan.

Malformed pending data cannot authorize a snapshot attempt or a guessed watermark. If it becomes malformed after an attempt, terminal handling erases it without advancing any scope, including an otherwise valid row in the same invalid array. Existing expiry and seven-day job cleanup still apply; no quarantine/history table or extended retention is introduced. This fallback does not claim to reconstruct delivery/progress after corruption.

An attempt is the existing durable marker/attempt-start claim, not proof that a provider was invoked or delivered mail. Uncertain finalization may suppress mail after a crash before transport, preserving the previously chosen conservative attempt semantics. Already in-flight mail cannot be recalled. Sending, immediate transport reauthorization, producer completeness/immutable retrieval, provider configuration and production cleanup wiring remain separate gates.
