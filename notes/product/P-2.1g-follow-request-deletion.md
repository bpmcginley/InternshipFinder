# P-2.1g dormant deletion of a pending follow request

Stacked on frozen P-2.1e `e1a79e49`. The trusted dispatcher can mint one deletion-only bearer for a live confirmation token. It stores only the new bearer hash and a foreign key to the confirmation hash. The `fd_` bearer has the existing UUID-plus-secret suffix recognized by the mail renderer's public-link guard. The capability inherits the confirmation expiry. Confirmation, reissue, cleanup, and subscriber deletion remove it by cascade. A repeated mint does not rotate an issued capability. Reissuing a message requires a fresh confirmation token.

An explicit deletion call removes only the current unconfirmed scope and its confirmation token. If the scope is already active, only the pending confirmation or account-link change is canceled. A subscriber is removed only when unconfirmed and left without any follows. The operation is a single D1 batch, so a concurrent confirmation or reissue cannot revive a deleted request or let an old link erase the new request.

Additive migration `0007` and the equivalent legacy schema preserve outstanding digests when an unconfirmed scope is removed. Removing a confirmed scope still cancels its subscriber's outstanding aggregates. Existing migrations and the independent send-day marker are unchanged. The skipped sequence numbers on this stack are reserved for separate top-up work.

Future routing must show a read-only preview and require explicit POST for this bearer. It must keep the request-only body link separate from address-wide RFC 8058 unsubscribe, use generic responses, redact bearer URLs and preserve deletion when signup and sending are off. No routing, dispatcher, mail, copy, runtime activation or deployment is included. All tests use synthetic recipients and local databases.
