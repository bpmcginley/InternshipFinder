# P-0.2 counter review

Updated: 2026-11-10. State: merge authorized; disclosure and deployment remain gated. Bruce authorized the refactor lead to finish and merge PR #175 after review and green checks. This note proposes privacy wording for separate approval; it does not change the published policy. Worker deployment remains an operator action after approved disclosure is published.

## Change

Accept these 16 fixed browser event names in the existing `/hit` allowlist:

`group_expand`, `major_quick_set`, `save_role`, `mylist_open`, `share_click`, `list_link_click`, `widget_link_click`, `out_of_runs_view`, `out_of_runs_invite`, `out_of_runs_topup`, `out_of_runs_plan`, `follow_open`, `follow_submit`, `follow_confirm`, `demo_play`, `flyer_print`.

Only the existing `event_counts` columns are written: UTC day, fixed event name, bounded page kind and count. No schema, user identifier, company, role, major, search, email address, campaign attribution or retention change. Existing origin, bot, rate and daily-cap checks still apply. Existing aggregate event totals have no automatic expiry. They cannot be linked to an account for individual deletion; an operator can delete aggregate rows. This PR adds no client emitters and no user-visible strings.

The existing client counts a given event at most once per page load. These totals are not unique people or every repeated interaction. `follow_confirm` is only a browser-observed confirmation-page signal. It is not proof of a confirmed subscription, just as `out_of_runs_topup` is not proof of a purchase or `flyer_print` proof that a printer produced a page. Any future server-verified follow outcome requires its own reviewed implementation and policy wording.

## Verified rollout behavior

Before this change, `docs/js/count.js` sends unknown names without waiting for a response; `worker/src/visits.js` returns `{ counted: false }` before database access. An in-memory test of the unmodified source sent `group_expand` once, rejected it without database access and made no network request. The HTTP route returns 204 for ignored names. Later site packages can send the new names before deployment, but those names will not be recorded until Bruce deploys this worker change.

The policy's current count paragraph (`docs/privacy.html`, Searching listings section) lists actions explicitly. It does not name all these new actions. That is a wording approval gate, not evidence that the existing policy already covers them. Do not deploy these counters until Bruce approves the matching disclosure.

## Exact proposed addition to the count paragraph, not approved

Insert after the sentence ending "as totals that say nothing about who":

> We also count expanding a company's results, choosing a major, saving a role, opening My list, pressing a share link, opening our GitHub list or widget page, seeing the out-of-runs panel, and pressing its invite, top-up or plan controls. We count opening or sending a company or search email-follow form, reaching its confirmation page, playing the demo, and pressing Print on a flyer. Each of these browser steps is counted at most once per page load, as a daily total by step and kind of page. These counts contain no account ID, email address, company, role, chosen major or search terms. They do not prove that an email subscription was confirmed, a purchase completed, or a flyer printed. These aggregate totals have no automatic expiry and cannot identify a person's activity for individual deletion.

This addition describes counters only. It does not approve follow-subscription storage, sending emails, top-up payments, or cross-device saved roles. Those remain separate design-note gates. The future policy PR must align its wording with features actually enabled at publication time.
