# P-2.1ee Follow archive enqueue continuation

Design for review. A daily Follow archive sweep needs to finish across multiple bounded invocations when a single invocation runs out of work budget.

## Measured limit

At the 100-statement ceiling, an actual local Workers/D1 sweep queued 19 of 19 synthetic subscribers in 97 statements and 40 binding calls. With 20 subscribers, two fresh passes each revisited the first 19 and left the twentieth untouched. The deployment adapter independently reproduced that partial result. Raising the configured subscriber count cannot remove the statement ceiling. Confirmed subscribers accumulate across days, so a daily signup or send allowance cannot establish complete-pass capacity. [Native evidence](https://github.com/bpmcginley/InternshipFinder/pull/630#issuecomment-6846262939) · [Runner contract](P-2.1dw-archive-release.md)

## Private state and deletion

Keep one D1 record for the current daily sweep. Bind it to one UTC day, the exact catalog and archive pins, the existing enqueue cutoff and an opaque execution generation. Store a nullable reference to the last accounted subscriber and a flag for unresolved results. The reference is the existing internal subscriber ID and identifies a subscriber while that row exists. Keep email addresses, scopes, job IDs and per-person results out of the record and logs. Emit only aggregate outcomes and work counts.

Subscriber erasure must clear the reference and invalidate the generation in the same transaction, including unsubscribe, last-scope removal and account deletion when they erase the subscriber. If a scope or account link is removed while the subscriber remains active, the cursor retains only that subscriber reference. Distinguish an invalidated empty cursor from the empty cursor of a fresh sweep. A restart from the beginning must earn completion again. Delete-and-recreate cannot restore the earlier generation.

Set expiry to the earliest of the existing archive enqueue cutoff, catalog release cutoff and end of the UTC day. Erase the expired record through separately qualified send-free maintenance, including when enqueue is disabled. Stale or unresolved state closes continuation. There is no cross-day history.

## Progress and replay

- Resume one logical daily sweep of the same pinned snapshot. Reuse the ordered confirmed-subscriber seek, per-subscriber enqueue transaction and daily uniqueness. A same-day queued result must match the exact subscriber, scope generations, day, snapshot digest and pending advances. Delivery stays under its existing separate owner and shared budget.
- Advance the cursor only after every examined result in a page has a valid receipt. A verified gap, invalid scope or CAS conflict can be accounted as unresolved so the sweep reaches later subscribers. The unresolved flag prevents a complete result. A missing or contradictory receipt withholds the page checkpoint. On re-examination, require the existing exact idempotency and watermark checks for earlier acknowledged writes.
- Fence checkpoint writes and new queue or watermark mutations with the same generation, day and cutoff. Reconcile an uncertain checkpoint write only against the exact intended predecessor revision and successor generation, pins, cursor, cutoff and unresolved bit. A later revision cannot acknowledge an earlier write. Changed same-day pins require a fresh sweep from the beginning under a new generation, with the existing same-day queue uniqueness and exact replay checks. Preserve the rules for transactions already admitted and for uncertain email delivery.
- Open the sweep generation only after database UTC reaches the pinned snapshot timestamp. Use the same strict `confirmed_at < snapshot timestamp` scope cohort in indexed subscriber enumeration, the bounded progress read and the enqueue transaction's full-set check. Confirm a new lifetime with one database-UTC sample for its confirmation timestamp and initial watermark in the same mutation. Current code uses caller time, so this requires separate runtime qualification for delayed commits, nonregressing database time and restore. Later confirmations cannot enter the open cohort. A role first seen by the snapshot cannot match a scope confirmed at or after that timestamp. Reconfirmation preserves the original lifetime. A removed and recreated scope gets a fresh generation. Preserve historical timestamps and report partial for ambiguous records.
- Later scopes outside the cohort must not invalidate an exact same-day queued receipt. A later day starts at the beginning. For deferred scopes, verify that the next snapshot's coverage starts at or before the unchanged watermark. If bounded evidence cannot establish coverage, report partial. A full rescan with the same work ceiling cannot prove coverage beyond its acknowledged frontier.

## Qualification before activation

Verify the actual D1 writes and receipts under maximum all-match workload, concurrent invocations, process restart, lost acknowledgement, subscriber erasure, scope confirmation behind the cursor, cutoff, UTC rollover, missing snapshots and database restore. Budget the added state reads, fences and checkpoint writes within each invocation's existing limits. The measured 19-subscriber limit may be lower with this overhead. Demonstrate completion within the existing enqueue window. Keep enqueue off until this design or a verified complete-pass approach qualifies.

Approval is required for the single retained subscriber reference, its lifetime and erasure, and bounded continuation of one daily sweep. Email content, provider cap and existing subscription and archive retention policies stay as approved. This proposal adds no schema, trigger or production configuration.
