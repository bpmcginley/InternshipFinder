# P-2.3t published employer catalog mode

Draft [#406](https://github.com/bpmcginley/InternshipFinder/pull/406) is a child of exact reviewed #404 `58ce0fb6`. It changes only employer-posting-runtime.js, a new standalone local Workers test, coordinated API.details.md/generated API.md, this note and STATUS. No descriptor, production configuration or activation is added.

`EMPLOYER_POSTING_CATALOG` accepts the existing exact `{url,version,sha256}` descriptor unchanged, or exactly `{mode:"published",url}`. Both require the existing enabled switch and the fixed approved `https://internscout.org/data/employer-posting-keys.json` URL. Mixed fields, unknown modes and other URLs fail closed. Pinned mode retains its version query, raw-byte digest check and request options. Published mode requests the same keys-only array without a version query, using explicit GET, `cache:"no-store"`, `redirect:"error"` and `credentials:"omit"`. It trusts the approved first-party publication, not an independent release digest. No additional digest state is computed or retained for this mode.

The shared canonical parser, 256 KiB stream bound, five-second request-owned deadline, five-second failure retry delay and five-minute load-start cache lifetime remain. An A-to-B publication is picked up on refresh without changing the descriptor; removed A keys then stop authorizing counts. A valid cached A may remain usable until its hard expiry. Refresh failure never extends that lifetime. A competing request does not await or cancel another request's response, reader or timer. Mode/configuration changes invalidate old generation leases, including delayed loaders. No D1 binding or request object is retained by the isolate cache.

Cloudflare's [fetch cache documentation](https://developers.cloudflare.com/workers/examples/cache-using-fetch/#using-the-http-cache-api) describes `no-store` as bypassing cache and not storing the fetched response. Its [compatibility documentation](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#enable-cache-no-store-http-standard-api) makes this option default from November 11, 2024; the existing Worker compatibility date is September 1, 2026. The local workerd Request constructor accepted the option without configuration changes. These checks do not claim a production CDN or origin freshness probe. This mode consumes the bytes currently served by the trusted fixed URL; deployment propagation and publishing annotations plus their matching catalog together remain separate release gates.

Validation: Node 22.23.4 passed all 726 Worker Node tests. Pinned local workerd 1.20260911.1 passed 288 tests across 52 files, including nine new synthetic local D1 cases. New cases cover explicit/mixed descriptors, A-to-B refresh and removal at the exact lifetime, failed refresh/recovery, canonical and stream bounds, late fetch/body, concurrent request ownership, late-owner replacement, exact pinned compatibility, mode changes and switch-off invalidation. The clock harness advances the admission and cache clocks together within one synthetic database day. No external requests are made; injected fetch returns synthetic Response objects. These new tests exercise concurrent calls inside local workerd, not a new production or multi-invocation network probe. Existing cache ownership source and prior runtime probes are unchanged. Prettier, ESLint, generated API verification and diff checks passed. Independent review and exact CI remain required.

Index, scheduler, Wrangler, publication, allowlist, App, golden artifacts, schema and migrations are untouched. No new user fields, public catalog facts, visible copy, provider calls or deployment are introduced. Same-release site publication and maintenance qualification still precede collection enablement.
