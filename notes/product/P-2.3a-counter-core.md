# P-2.3a isolated employer counter core

Partial implementation of the approved [P-2.3 design](https://github.com/bpmcginley/InternshipFinder/pull/209), based on main `4c65e595`. **Unwired, draft and not deployed.** No published policy or new production collection. Owns only the new core, new focused tests/test-only schema and this evidence/tracker entry.

- Internal parsed payload is exactly `{e: "employer_posting_open", c: publicCompanyKey}`. The eventual route must apply existing origin/body/bot checks, then dispatch before the old minute limiter. The current production `/hit` ignores this event; both Node and actual local Workers tests prove no aggregate row or new table is created.
- The injected snapshot is copied into a private membership set. Missing, empty, duplicate, invalid or oversized snapshots fail closed: at most 10,000 distinct keys and 200 UTF-8 bytes per key, no control characters or malformed Unicode. The core does not derive canonical keys, fetch a catalog or pick a cache lifetime.
- A dedicated instance-local map allows 30 requests per address per UTC minute and at most 2,000 addresses; new entries are rejected when full. An expiry timer clears idle address entries at the minute boundary; request-time rollover also clears them. It contains only addresses/counts, never company associations. Address strings come from the future trusted request adapter, are bounded to 64 characters, and never enter SQL/logging. Invalid payload attempts consume this independent budget too. Missing addresses fail closed. The isolate-wide budget is shared across core instances and survives snapshot replacement; keep the core cached rather than recreate it per request.
- One D1 SQL statement conditionally increments `(day, company, n)`, enforcing 1,000/company/day and 50,000/day across instances. No persisted rollup or identity. Time is server-injected; client day/count/extra fields and unknown keys are rejected. Client once-per-company/page deduplication remains a separate emitter requirement, not a claim of this server core.
- Successful cleanup is required before counting on each UTC day. It deletes days strictly older than the previous 90 UTC days, retaining today's incomplete bucket plus 90 completed days. Cleanup failure disables that instance until a successful cleanup; old cleanup completion cannot enable a new day. No replay or rollup. Future cron/health integration must enforce the approved retention-failure collection gate across deployed instances; admin reads must independently exclude expired/incomplete days. No admin reader is implemented here.
