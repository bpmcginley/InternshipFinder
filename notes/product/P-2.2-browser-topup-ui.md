# P-2.2 native browser top-up UI

Draft [#429](https://github.com/bpmcginley/InternshipFinder/pull/429), started on `baf163d8` and normally integrated with main `54b9aa16`, changes only native allowance/dashboard modules, focused tests and package evidence. Classic App/Core, graph builder, allowlist and publication workflows stay unchanged. Both shared golden artifacts were refreshed after the explicit coordinated handover. The separately owned Worker offer/capability contract is required before this detached UI can appear. Owner enablement and independent review remain gates.

The panel requests an offer only when the current session has an exhausted, enabled, finite allowance and `/config` explicitly reports `topups: true`. That flag is a hint: only a fresh no-store `GET /billing/topup/offer` response with `enabled: true` and exactly USD 300 cents / 25 units reveals the purchase copy. Signed-out, legacy ID-token, paused, non-exhausted, unlimited, disabled, loading and absent-capability states make no offer request. The server remains authoritative for eligibility and actual Stripe Price verification.

An explicit accepted click makes one bearer-authenticated, bodyless `POST /billing/topup/checkout`. The tagged action lock prevents a top-up from overlapping billing and prevents billing during an active top-up. Existing subscription/portal requests still supersede earlier subscription/portal requests through their original sequence guard, including across account changes. Requests use no-store, omit credentials/referrer, reject redirects, and bound the entire fetch/body operation to eight seconds and 16 KiB with abort plus elapsed-clock checks. Auth generations, panel context and request sequences fence late results, including A-to-B-to-A account transitions. Only HTTP 200 with `status: open` and the existing strict HTTPS `checkout.stripe.com/c/pay/cs_...` URL shape can navigate. HTTP 202, missing or invalid URLs, timeout and other failures show the approved unavailable copy; no creation/return state implies payment confirmation or pending payment. Retry re-verifies the offer. No return-query interpretation or storage is added.

The existing `out_of_runs_topup` aggregate goes through the existing once-per-page arrival counter only on a verified accepted Buy click. Passive render, offer load, retry and rejected clicks do not count. No identifiers, price, account or URL payload is added.
