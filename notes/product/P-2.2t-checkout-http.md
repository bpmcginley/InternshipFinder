# P-2.2t dormant checkout HTTP boundary

Draft [#353](https://github.com/bpmcginley/InternshipFinder/pull/353) on exact #345 `f66812e96c7ed1e9a7a41f1e9f512827f0474bee`. New standalone `topupCheckoutResponse` adapts an incoming POST to the reviewed session-fenced checkout service. The existing session lookup gains an opt-in read-only mode, preserving all default callers. No router, auth.js/http.js, schema, billing, limits, provider, public copy, policy defaults or activation changes. Needs-bruce: owner integration, parent merges and release gates remain.

## Boundary

Only the Authorization header can supply an existing `iss_` session bearer. Cookies, provider ID tokens and query tokens cannot authenticate. The default uses existing `sessionUser` with the new `refresh: false` option, reusing its private hashing, token validation and lookup without sliding expiry. All existing callers retain `refresh: true` by default. No OIDC key fetch is possible. A fresh monotonic Worker clock validates the returned identity and original expiry after authentication resolves, then the exact authenticated user and same bearer go to #345. That service retains the reservation, final session/attempt association, revocation and post-read expiry checks. Authentication and checkout functions are trusted dependency-injection seams for tests/integration, never request fields.

The handler does not read or forward request body/query fields. Price, units, owner, adapter, callbacks and return URLs remain server-owned. Only a server-verified adapter is accepted by the existing service; omission stays disabled. The future router still owns origin/CORS, request infrastructure and route selection. No endpoint is registered here.

Every response is JSON with `Cache-Control: no-store`. POST outcomes are `open` with verified checkout URL (200), `pending` (202), `auth` (401), or `disabled`/`unavailable` (503). Other methods receive 405 and `Allow: POST`, without authentication or checkout. The output explicitly selects these fields, defensively validates the Stripe checkout URL shape, and discards errors, attempt/provider/account data and unexpected fields. Error text is never logged or returned. The URL itself is intentionally private response data, not a logged or stored artifact. Repeated uncertain creation remains pending; no new POST is initiated by this wrapper.

## Why retention deletion was not implemented

The approved 400-day schedule starts after zero balance and financial resolution, not purchase creation. In this exact parent, `topup_purchases` stores only `created`; reconciliation records flags/revision without resolution time, and allocation/restoration can change zero balance without a qualifying-state timestamp. Two purchases can have identical stored rows but have become empty/resolved at different times. Using creation plus 400 days would delete a recently exhausted or resolved old purchase. Allocated receipts also remain restorable independently of run cleanup; treating consumption as final would assume the unapproved #294 lifecycle/late-callback rules.

No existing authoritative timestamp establishes the approved deletion threshold, and this package does not introduce a speculative clock, storage field or deletion operation. The approved retention policy remains required; its safe clock and mutation coverage must be resolved in a separate package. Existing terminal fingerprint preservation and account-deletion trigger remain unchanged.
