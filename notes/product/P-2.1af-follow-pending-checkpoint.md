# P-2.1af Pending follow lineage checkpoint

This dormant leaf implements the pre-push record in the approved [P-2.1ab design](https://github.com/bpmcginley/InternshipFinder/pull/358) at `b34ea29b`. The trusted caller supplies the original complete in-process writer proof, typed staged receipt, actual candidate commit, observed UTC time and explicit byte and row bounds. The expected predecessor binds its commit, public tree and accepted checkpoint SHA-256. A null checkpoint SHA-256 means the caller independently established absence for an approved forward seed.

Preparation checks the candidate's raw single-parent commit and exact staged tree. It verifies owned paths and the immutable candidate index and shard bytes with replacement objects and lazy Git fetches disabled. A no-op cannot start a new generation. The canonical record holds the old identity, candidate identities, coverage, source hashes and sorted evidence tuples, including closed listings. It carries no URLs. Its SHA-256 names one pending generation. Recovery revalidates the record with independently supplied current predecessor identity, local Git objects and a trusted clock. It accepts a record before its exclusive 24-hour deadline and reconstructs the full lineage. The restricted record must come from trusted preparation and storage.

A scratch SQLite/Git test reads pending bytes after the index and working files change, revalidates a scratch candidate index through the staged-proof validator and binds a synthetic later same-tree commit through the existing typed accepted Git check. The resulting accepted checkpoint retains closed lineage and its verified timestamp. The test uses no Git remote.

A future caller must persist the pending generation before push, independently observe accepted Git, reverify through the typed binding and promote by durable CAS. Missing, stale or expired proof holds follow planning. No writer, workflow, public output or storage behavior changes. G3, integration and operator configuration remain gated.
