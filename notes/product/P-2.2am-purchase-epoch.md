# P-2.2am purchase history epoch candidacy

Base: exact main `deebe26def722ee99fda660e65cf0c717bfe6983`. Implements only the nullable purchase epoch allowed by the approved [history design](https://github.com/bpmcginley/InternshipFinder/pull/530). No production caller opts in.

`captureTopupEnrollment(db, attemptCapture, livemode, {enabled:true, schemaKey})` reads a qualified coverage row and the still-active original attempt/revision together. The original attempt creation must lie inside the captured coverage window, whose upper bound cannot exceed database UTC. A strict successful read returns an opaque, frozen, isolate-local authority bound to this exact DB, attempt revision, original creation, mode, epoch, schema and coverage bounds/revision. No serialized object can recreate it. Missing or unqualified coverage does not create authority.

The optional seventh argument to `settleFirstTopup` binds that authority synchronously before awaited settlement work. Its existing transaction inserts nullable `topup_retention.coverage_epoch` only when the entire qualified tuple still matches and the database-observed capture time strictly precedes settlement database UTC. Equal-millisecond or reversed clocks conservatively leave NULL. The caller's purchase `Date` is not chronology authority. Rotation/closure/schema/bounds/revision changes leave NULL without withholding the normal financial grant. Existing retention refreshes cannot set or rewrite the epoch; replay and deletion never backfill it. The retention row retains its original purchase-deletion cascade.

This is **candidacy only**. An attempt predates its associated Checkout, but does not establish the independent first-settlement event time. Current payment evidence supplies no trusted event timestamp. Later retirement must independently prove that event boundary, uninterrupted qualified coverage through its decision, financial/retention fences and restore continuity. This package neither invents that timestamp nor qualifies any epoch, changes `history_proven`, or enables erasure. Historical purchases remain NULL. Migration 0034 must be applied before explicitly enabling capture/settlement integration; omitted authority preserves pre-0034 SQL and financial behavior.

Owned paths: additive migration 0034, repeatable legacy schema, migration parity test, the two existing settlement/retention modules, one native test and this note. Migrations 0001–0033, replay, routes, provider configuration and retention policy are unchanged.

Validation: 86 actual local workerd/D1 cases across enrollment, migration parity, first settlement, retention, coverage, purchase recovery and history replay; 62 focused Node 22 cases across the existing settlement/retention/coverage/replay/recovery/reconciliation suites. The 18 new native cases include exact tuple invalidation, late batch-arrival rotation, historical and copied authority, cross-attempt/revision/binding rejection, malformed acknowledgement (including zero-getter own-data receipt snapshots and a forged-results getter over an actually absent attempt revision), legacy pre-0034 settlement, cascade, rollback and committed lost acknowledgement. The equal-clock fixture substitutes only the capture-time bound with the same native SQLite expression to deterministically exercise equality; all financial statements remain real. Two direct comparisons against the base confirm omitted-option SQL and bind arguments byte-identical. ESLint, Prettier and diff checks pass. No external provider or live database was used.
