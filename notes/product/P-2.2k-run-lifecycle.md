# P-2.2k run lifecycle proposal

Design for independent review and Bruce’s approval. The public `run_id`, UTC-month identity, per-run call cap and monthly → invite → oldest purchased funding order stay as specified. A supplied ID groups calls and can be reused after a failed run. Omission creates a fresh solo run. Purchased funding remains dormant.

## What the current code does

At main `0de0eb4c`, [admission](../../worker/src/limits.js#L280-L322) publishes a zero-call row before funding. [Release](../../worker/src/limits.js#L425-L458) trusts the first call’s `isNew` flag. [Settlement](../../worker/src/limits.js#L462-L517) has no per-call fence. [/ai](../../worker/src/index.js#L367-L394) releases a rejected upstream call and settles after response metering.

In-memory SQLite probes ran those functions with six-cent synthetic estimates. Releasing run A twice left run B present but reduced usage and both day and month spend from 1/6¢/6¢ to 0/0¢/0¢. A delayed release deleted a replacement using A’s ID. With two admitted calls sharing an ID, releasing the first and settling the second left zero runs and units despite the second call completing. At a full allowance, pausing the creator before its usage write let a follower enter through its provisional row. The creator then received the cap error and deleted that row. No HTTP or provider requests ran.

## Transaction rules

1. In D1, publish a run generation only with committed funding, the first call slot and the call’s exact accounting reservation. Additional calls acquire their own slots under the same funded generation. Preserve current task, rate and budget gates. Keep purchased funding off while implementing and verifying this boundary.
2. Use the exact server-generated call ID and generation for each compare-and-set. A reserved call can become released or accepted once. An accepted call can be metered once. Gate every dependent write on its transition in the same transaction. Release returns only that call’s estimate and slot. Metering reconciles spend and tokens. Preserve the first-Auto-Apply event once when an eligible generation first receives a usable response.
3. Retain funding while a sibling is pending or any call was accepted. Refund the recorded source once when the last call definitively fails and none was accepted. The same public ID can then acquire a new random generation. Mark an accepted upstream response before exposing it. Metering failure, stream interruption and ambiguous Worker loss keep the charge and estimate unless authoritative accounting arrives. Legacy rows continue with existing calls treated as committed and no inferred refundable funding. Drain old handlers before enabling the new writer.
4. Extend [#254 receipts](P-2.2d-allocation-implementation.md) to distinguish generations. Each generation’s allocation and reversal must be atomic with its run transition. Restore only to the original purchase under its current available, held or revoked disposition. Integrate purchased funding last, after monthly and invite exhaustion and with the account deletion fence in place.

## Retention and owner decisions

Existing [cleanup](../../worker/src/limits.js#L555-L577) aggregates and removes earlier-month run rows at the first successful daily sweep after UTC month rollover. The [configured schedule](../../worker/wrangler.toml#L19) is 07:17 UTC for this cleanup. Account deletion keeps current-month allowance counters until that sweep. Propose keeping only server-random generation and unfinalized call IDs, funding and outcome flags, and numeric accounting coordinates under that same sweep. Terminal call IDs can be discarded once the transaction commits, since an absent ID cannot authorize a write. Use the captured month for callbacks until its sweep. After the sweep, ignore late callbacks and retain their estimates. Store no prompt, reply, provider request ID or new account identifier.

Purchase receipts remain under approved purchase retention. They cascade on purchase deletion and otherwise follow the 400-day resolved-zero rule. The proposed retained receipt adds only a random generation discriminator to existing run/purchase linkage. Also confirm whether a later call may join a generation whose purchase became held or revoked after funding.
