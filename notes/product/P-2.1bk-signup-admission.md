No HTTP route, schema/migration, limits.js change, provider, configuration, public copy, publication or activation.

`admitFollowSignup(db, input, {enabled=false, dailyLimit, catalog, clock})` accepts only the exact parsed shape `{email,scope,link}`. It is disabled unless enabled is exactly true; the positive safe-integer global limit and a trusted already-validated signup catalog are mandatory. It copies the catalog Sets and canonical scope before any awaited storage. It does not accept a catalog, rate identity, clock or limits from the request. Missing/extra keys, invalid email/scope and nonboolean link fail before any database access. `link:true` returns `unsupported` without storing an unlinked follow. Only explicit `link:false` is admitted; scoped account linkage remains separate.

Email normalization and validation now live in exported `normalizeFollowEmail` inside follows.js. The existing request writer calls that same helper; its prior trim/lowercase/254-character/regex behavior and error remain unchanged. No dots or plus aliases are merged. Scope validation reuses unchanged `canonicalFollow`, including unknown/remote rejection and existing selection limits. A future HTTP boundary must provide bounded body parsing, approved consent/copy, safe responses and Origin handling. This internal parsed-object function is not that boundary.

## Admission ordering and privacy

After validation, the helper invokes unchanged `bumpUnder` with the fixed anonymous sentinel `*follow-signup` and `d:YYYY-MM-DD` bucket. It cannot collide with account SHA-256 identifiers or the existing AI `*` sentinel. No IP, address, account, request token or derived identity enters the rate table. The existing `limits.cleanup` d-prefix sweep removes old buckets using its existing two-day cutoff; this package adds no cleanup task or retention policy. It never resets an active cap on deletion or restart.

The cap counts valid admission attempts, including duplicates and subsequent uncertain queue outcomes, not unique addresses or sent mail. Admission is one conditional SQL mutation, so concurrent requests cannot exceed the supplied cap. Cap rejection, invalid configuration or unavailable/ambiguous storage returns only `unavailable`. The helper requires explicit successful D1 metadata before treating the conditional mutation as admitted. It samples the trusted Worker clock again after rate admission and rejects backward time or UTC rollover before queueing. The bucket belongs to that admission day; no retry into another day is attempted. Clock/source accuracy and later mail-send caps remain separate caller/operator responsibilities.

After a definite admitted budget slot, the unchanged `requestFollowConfirmation` transaction creates/deduplicates the pending scope and its confirmation queue. All returned D1 batch results must explicitly succeed, and the internal receipt must match the exact scope and expected identity shapes. The public-facing helper result is only `{status:"accepted"}`, identically for a new pending request, an existing pending request or an already confirmed scope. No subscriber/job/scope identity is returned. No existence lookup precedes the cap. Original pending expiry is preserved on duplicates.

Budget reservation and queue transaction are intentionally separate. A failed queue or lost acknowledgement may consume a slot without a confirmed receipt; it is never refunded or automatically retried. A lost queue acknowledgement may already have created the pending job. A later explicit request consumes a new slot and safely deduplicates through the existing transaction. This conservative under-use preserves the cap without adding replay identity/storage. No sender or transport is invoked.
