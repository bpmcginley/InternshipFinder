## Publication-to-admission trust chain

1. **Qualify the writer and selected export first.** Retain the verified run/attempt, data commit and raw public tree provenance described in [P-2.1cr](P-2.1cr-writer-publication-handoff.md). Workflow source SHA and data SHA are different facts. A matching Git tip or trailer alone does not prove the accepted writer operation. Keep ordinary listing success independent of private checkpoint recovery. The held writer/catalog/publication stacks still need normal integration and qualification after G3. This note does not treat their draft source as deployed.
2. **Produce catalog and page identities from the same original bytes.** The held catalog producer/stager/raw-Git reader (#510/#518/#522), same-export company mapping (#570), and coordinated annotation staging (#580) supply the relevant source contracts. Bind canonical catalog bytes to their exact source digest and their own catalog digest. Verify emitted Follow controls reference that catalog's signup keys; do not derive identity again from a display name or URL, or feed an already transformed employer export into a differently pinned producer. Qualify the actual selected Pages artifact and served first-party bytes, including removal on rollback. No private checkpoint content belongs in this public artifact.
3. **Carry prior valid-key continuity independently.** A release authority must supply the exact prior approved public `valid` company/field/state sets from a verified predecessor, not from the proposed new catalog alone or an isolate's incidental cache. The parser requires every prior valid key and every current signup key to remain in `valid`; `signup` can narrow without invalidating existing scopes. Three empty sets are valid only for an explicitly established genesis, never a restart, missing predecessor, failed read or restore. Public predecessor pins/bytes may be carried through the existing reviewed publication evidence; this note chooses no new persistence service. Missing or unverifiable predecessor evidence closes admission. An old catalog is not a safe rollback if it drops keys introduced by a subsequently approved release.
4. **Create one immutable trusted release snapshot.** Reuse the existing supplier shape exactly: `{dailyLimit,deadlineMs,maxBytes,maxKeys,origin,previousValid,release}`, where `release` is `{url,sourceSha256,catalogSha256,notBefore,expiresAt}`. `previousValid` becomes fresh owned Sets after validation. The operator release process must prove the origin, pins, predecessor and UTC interval together. A version string, mutable first-party URL, self-declared source hash or fresh fetch alone cannot grant this authority. Do not mix an old predecessor with a new payload or independently sample configuration after awaits. Store no email, scope or capability in this descriptor.
5. **Connect production to the existing supplier.** The smallest source package is a bounded, strictly validated deployment-input adapter feeding `prepareFollowSignupAdmission` before body admission. No key name, JSON size, TTL, cap or production default is selected here. Missing, malformed, incomplete or expired input keeps the existing closed response. Preserve app-clock checks through hashing/rate work and the first SQL guard in the same atomic queue batch. No current-time extension, stale fallback or automatic genesis is permitted. Supplier validity qualifies signup admission, not mail or archive coverage.
6. **Independently qualify the archive for existing scopes and delivery.** Use the reviewed first-party manifest, retained immutable snapshot pins, coverage and original cutoffs through `createFollowArchiveReader`. Feed existing-scope matching the catalog's `valid` sets, not only `signup`. A listing release or valid catalog does not establish Follow timestamp coverage. Gaps, unavailable snapshots and expired admission windows hold enqueue without watermark advance. Delivery rereads the pinned snapshot already attached to the queued job; a replacement latest snapshot cannot substitute for it.

Frozen writer requalification is part of this dependency chain. The lead's exact `c4056b78` merge previews for #488 and deadline child #501 report conflicts only in `backend/tests/test_ingest_data_writer.py` and Product STATUS; #522 reports only STATUS. This is mergeability evidence, not proof of runtime compatibility. Normal integration must preserve current #537 run/attempt/commit/tree output and same-attempt Pages verification, then rerun the file-only Git, deadline, no-op, lost-acknowledgement and ordinary publication fixtures. Preserve the current source of selected listing pins. No writer edits or branch refresh are included here.

The current entry already exposes `FOLLOW_MANAGEMENT_ENABLED`, `FOLLOW_MANAGEMENT_REQUEST_ENABLED`, `FOLLOW_MANAGEMENT_REQUEST_TTL_MS` and `FOLLOW_MANAGEMENT_REQUEST_DAILY_CAP`. Those govern management admission only. They do not select a sending cap or schedule. The proposed signup supplier must not overload them or silently turn any endpoint on.

## Actual scheduled entry and bounded work

A subsequent mounting package should make the real scheduled handler delegate only an explicitly qualified Follow invocation to the existing ports. Preserve the current clock early return, student-billing branch, campaign-report branch and daily financial cleanup exactly. Never let a new Follow event fall through to unrelated daily jobs. Do not add Follow work to `4,34 * * * *` merely because that clock already exists. The operator-approved trigger/cadence and D1 allowance must be recorded before selecting or changing a production trigger.

The intended integration has separate admissions for send-free maintenance, archive enqueue, link delivery and digest delivery. Disabling sending must leave independently qualified maintenance possible. The dispatcher takes one trusted snapshot of binding identity, policy functions, catalog/archive authority and explicit work bounds per invocation. It selects only permitted work for that invocation; it must not run every category concurrently through `Promise.all`. The exact fairness and frequency between links and digests remains part of cadence qualification. Link confirmation/management alternation already belongs to the durable owner and must be reused.

Any new index, persisted continuation or retention decision must be separately scoped and reviewed.

## Approved ownership versus outstanding operational authority

Bruce approved [#563's owner design](P-2.1cq-delivery-owner-design.md). Implemented link/digest wrappers supply the shared generation, ready/running/held phases and exact continuation. Preserve the approved no-reset rule: elapsed time, expiry cleanup, process restart, a late provider response or budget day rollover cannot release running/held ownership. Independent maintenance may redact only obsolete references and must preserve generation, phase and turn. It cannot recall an email already handed off. Do not add an automatic lease reclaim or infer recovery permission from this note.

A clean acknowledged completion may advance the exact owner's validated continuation. Lost acknowledgement after that clean CAS is not a reason for a stale caller to overwrite a successor. Other uncertain outcomes remain held/running. A database restored before a spent claim can look ready and replay delivery; the record itself cannot prove restore safety.

The following remain required operator evidence, not new requirements invented by this design:

- Verified EMAIL entitlement for intended recipients, approved sender/postal/presentation and public action URLs, preview/retention settings, and delivered authentication/unsubscribe-header evidence. Synthetic Promise fulfillment proves the adapter contract, not actual provider acceptance or inbox delivery.
- Explicit shared provider allowance and reserve accounting for orders and other senders outside the Follow owner. Follow's daily D1 cap is not a provider-wide capacity proof.
- Independent restore/rollback authority protecting spent claims, budgets, ownership and private checkpoint lineage, plus an approved procedure and evidence before any uncertain hold can be released. No reset API or operator shortcut is proposed.
- Current migration adoption, actual entry/deployment identity, same-release first-party artifacts and catalog continuity, all required retention paths, trigger delivery and measured per-invocation/load budgets.
- Completed G3 and lead-coordinated writer/publication cutover. The current recorded conditional threshold is November 19, 2026 at 12:43:05 UTC, subject to seven clean days and lead release. It is not an unconditional launch date.

4. After the listed provider/restore/cadence evidence is accepted, qualify maintenance and the selected delivery lane before admitting new signup or management-request work. Verify released public action routes and already-issued capabilities. Activate only the separately authorized gates, with a monitored initial bound. No live verification is performed by this note.
5. Rollback closes new signup/management-request admission and sending first. It does not invalidate consent, erase issued capabilities or release owner holds. Keep confirmation, deletion and unsubscribe behavior available as required by the existing capability contracts, and keep qualified send-free retention running. Removing controls from a new Pages artifact cannot recall an open page or provider request. Retain valid-key continuity and referenced immutable snapshots under the approved retention policy; never repoint a queued digest at replacement bytes. A code rollback must preserve compatible schema/owner fences. A data restore stays sending-closed pending independent authority, even if the restored row says ready.
