# P-2.2o bounded payment evidence reads

[PR #314](https://github.com/bpmcginley/InternshipFinder/pull/314), stacked on frozen #311 `839aca54`. Needs Bruce for merge; no activation. Owns the payment evidence reader, its pure-test success fixture, shared Node/Workers boundary tests and registration, this note and own tracker entries. Shared billing, reversal, coordinator, routes, schema and production configuration are unchanged.

The complete payment-evidence GET phase has an absolute ten-second monotonic deadline, at most three requests, 256 KiB per response body and 512 KiB aggregate. The optional timeout can only shorten the deadline. Headers can reject early but never replace streamed byte accounting. Fatal UTF-8 decoding rejects malformed/truncated sequences. All existing payment/identity checks remain; the shared Stripe parser receives only bounded successful text. HTTP errors never reach its private-path/error logger.

Timeout or failure returns `pending`, aborts the transport signal and cancels bodies best-effort. Ignoring cancellation cannot yield later evidence or launch another GET. A blocking JavaScript turn cannot be preempted; deadline checks reject results after control returns. Injected transports must provide native Response streams. No live transport was invoked.

Validation: all 460 Node tests and 64 actual local Workers/D1 tests pass. Six new scenarios run in both runtimes: exact/one-byte-over individual and aggregate bounds; split multibyte and invalid UTF-8; missing/dishonest/invalid length, body and HTTP failures; stalled/dripping streams; one deadline across sequential GETs; abort, non-cooperative cancellation and late first/final responses. Recovery tests supply oversized paid and expired evidence: no claim, purchase, reconciliation or terminal attempt transition; the pre-read revision fence remains. Existing payment, expiry and recovery behavior also passes. Pinned JavaScript lint and owned-file formatting/diff checks are recorded in the PR. The existing local form-body Content-Type warning is unchanged.

These are technical resource limits, not price, allowance, provider quota or delivery promises. They do not bound D1, the separate reversal phase, or the whole recovery sequence; a future orchestrator still needs its own total budget and scheduling policy. Authenticated scheduling, existing-purchase reconciliation, #297, approved policy publication, private configuration, owner migration adoption and deployment remain separate activation gates. No work on #294 run lifecycle, public endpoints, provider writes or automatic retries. Public assets and golden fixtures are unchanged; UI screenshots/startup capture are not applicable.
