# P-2.1bf Checkpoint HTTP promotion

[#509](https://github.com/bpmcginley/InternshipFinder/pull/509) stacks on exact #507 `40a892712d9970bd524f5fd06e2962246931da85`. The dormant source implements the existing HTTP `promote(body, maxBytes, {predecessor, generation, checkedAt})` contract. The native SQLite/R2 harness mounts it for qualification. Production entry selection, legacy storage, bindings, workflow, provider and public assets are unchanged.

Promotion intrinsically copies the bounded accepted body and copies its option values before awaiting the canonical codec. It requires the exact staged generation, predecessor tuple, common payload and public tree. Acceptance cannot precede preparation. Checked-at cannot precede acceptance, and the database clock must have reached both. A live accepted predecessor must match all three predecessor fields. Initialized history cannot silently become genesis. The paired reader qualifies canonical metadata, physical payload and independent witness together before promotion.

The trusted `change(action)` port must repeat the predicate inside its synchronous SQLite transaction after witness preparation, using fresh database UTC time. It compares the complete captured control state and original pending/predecessor deadlines. The existing qualified native CAS is exercised directly. Promotion moves metadata to the already verified pending slot and retires the previous slot metadata. It never prepares or writes an R2 envelope. The final response requires a qualified read proving the exact accepted target. A missing/prepared witness or ambiguous commit remains unavailable until exact acknowledgement recovery succeeds.

The accepted control record adds one SHA-256 `promotionKey` over the original pending generation, predecessor tuple and accepted Git identity. This is the bounded completed-replay identity permitted by the [storage design](P-2.1an-follow-checkpoint-storage-design.md), retained with that accepted record. It contains no raw listing tuples or payload and disappears with the record. The paired reader validates its optional scalar shape. Older records remain readable but cannot acquire this new replay proof implicitly. Replay must match the key, generation, common payload and accepted Git identity before the earlier original pending/predecessor cutoff. It preserves the original accepted bytes, acceptance time, expiry and any newer pending candidate, including after retired predecessor cleanup.

The unchanged HTTP response is `promoted` or `already_promoted` with 200, known stale input with 409, and uncertain state with empty 503. Checked-at and original expiry never refresh on retry. This composition conveys no Git publication authority. Its caller must still supply independently verified publication evidence.

Qualification uses only synthetic native SQLite/R2 and the existing actual HTTP handler. Cases cover genesis and predecessor promotion, exact bytes and unchanged slot ETag, no PUT, original replay identity after cleanup, newer pending preservation, wrong generation/predecessor/payload/tree/time, intrinsic copying, concurrent calls, SQL rollback, lost witness acknowledgements, restored SQLite against an advanced witness and a real predecessor expiry crossing inside CAS. All 113 native cases pass, including 21 new promotion cases. The full Worker Node lane passes 809 tests. Pinned ESLint, Prettier and whitespace checks pass. Existing native tests remain registered unchanged.

Remaining release gates include production control/initialization and transaction-port implementation, exact-generation rejection, provider-qualified witness and restore proof, physical 24-hour/seven-day retention, and operation-wide I/O cancellation/deadlines. This package selects no provider and does not make the legacy body store qualified. No deployment, activation or sending occurs. Public screenshots and golden refresh do not apply.
