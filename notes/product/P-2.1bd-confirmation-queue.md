# P-2.1bd Atomic pending Follow confirmation queue

[#506](https://github.com/bpmcginley/InternshipFinder/pull/506) starts from exact main `1086e0ad`. It adds an unmounted `requestFollowConfirmation` path. A single D1 batch normalizes the address, saves the existing pending scope and inserts or retrieves one confirmation job for that scope. [D1 batch transactions](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

Migration 0021 starts with an empty queue, including on a database with existing subscribers, scopes and tokens. An explicit new request can queue an existing unconfirmed scope while it is within its original seven-day lifetime. It does not refresh the scope or rotate its existing token. Concurrent duplicates receive the same opaque job ID. Expired renewal creates a new ID. The same scope can get a different ID after deletion and recreation even at the same millisecond.

The queue stores only the opaque job ID, existing subscriber and canonical scope references, and queue and expiry timestamps. It stores no address, account ID, token or rendered message. Confirmation and scope lifetime replacement remove the job in the same transaction. The existing deletion and expiry paths cascade through the scoped foreign key. Failed enqueue rolls back the pending writes. Existing storage-only callers continue to work before applying 0021.

A future dispatcher must claim this exact job ID and recheck its unconfirmed scope and expiry in the transaction that mints the confirmation credential. Claiming the shared send budget and calling an approved sender remain later steps. This package does not dispatch, mount a request route, publish copy, change provider configuration or apply the migration remotely.

Local native D1 cases cover a populated upgrade, original expiry, concurrent deduplication, renewal at the cutoff, deletion and recreation, sibling preservation, expiry and transaction rollback. The exact migration and legacy bootstrap schemas match, including constraints and triggers.
