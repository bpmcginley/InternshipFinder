# P-2.1cy offline Follow release qualification

This test-only package starts from main `6adee49e271c68de005264a765bac7efdd14dab3`. It exercises the actual Worker HTTP entry, native local D1 migrations and the merged owned link/digest runtimes together. There are no production source, registry, configuration, schema, public artifact or shared STATUS changes.

The positive scenario requests an anonymous company follow through `/follows/signup` with a synthetic pinned catalog supplied through the existing trusted dependency seam. A duplicate preserves the same pending job and expiry. Owned confirmation delivery uses a synthetic email binding and the canonical renderer. The test extracts the confirmation capability from that rendered message, consumes it through the real HTTP endpoint and checks that replay returns 410.

Management request and duplicate request use the real HTTP entry. The owned link runtime delivers the management message, whose rendered capability subsequently lists and removes the exact scope. Before removal, the real archive reader verifies a synthetic manifest and snapshot, enqueue binds its digest and coverage, and the owned digest runtime reads the pinned archive again and sends one matching role. Three messages debit the same daily budget three times. The watermark advances, pending progress is removed, clean ownership returns to ready and a second digest invocation sends nothing.

Three adverse scenarios qualify the surrounding release boundaries:

- Default-off, malformed-email and wrong-Origin HTTP requests make no catalog or storage calls.
- An uncertain confirmation handoff retains the persisted held owner and spent budget. Newly constructed link and digest wrappers sharing that native database cannot send or reset it. This models loss of in-memory runtime state; it is not an actual provider restart or database-restore qualification.
- A deliberately lagging Worker sees an otherwise valid catalog release while actual SQLite UTC is already past its cutoff. The first queue-batch admission statement rejects atomically: no subscriber or confirmation job, no mail, and the admitted rate unit remains spent. No subsecond sleep or changed SQL clock is needed.

The initial owner record is seeded only by test setup. No scenario resets a held owner. All addresses, sender facts, capacities, release pins and archive data are synthetic; generated capabilities and messages remain in memory. Every catalog/archive fetch and email handoff is intercepted by an injected adapter. The positive scenario chooses an explicit test sequence, not a production fairness or cadence policy.

## Reproduction and evidence

From `worker/`, use Node 22 with `CLOUDFLARE_CF_FETCH_ENABLED=false`:

```text
node node_modules/vitest/vitest.mjs run --maxWorkers=1 test-workers/follow-release-qualification.test.js test-workers/follow-owned-digest-runtime.test.js test-workers/follow-signup-mount.test.js test-workers/follow-management-route.test.js test-workers/follow-archive-enqueue.test.js
```

All 49 actual local Workers/D1 cases passed, including four new scenarios. Pinned ESLint, Prettier and diff checks passed. The new file is automatically discovered by the existing `test-workers/**/*.test.js` configuration and normal hosted Workers lane; no standalone Node wrapper or shared registry import is added. Existing lock-identical dependencies were reused without a new installation.

This evidence does not establish a production sender, account allowance, preview retention, independent checkpoint witness/restore authority, shared capacity with order mail, hold-release procedure, cadence, or public catalog/archive publication. Those existing operator/provider/G3 gates remain. No live network, provider, recipient, workflow or activation was used.
