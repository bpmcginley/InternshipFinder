# P-2.2aq: dormant payment-history observation

Draft [#548](https://github.com/bpmcginley/InternshipFinder/pull/548) stacks on corrected #543 `10a4626a`, serializing migration 0029 after 0028. Bruce approved [#530](https://github.com/bpmcginley/InternshipFinder/pull/530), exact design `48be283b`. This package adds one observation/receipt-cleanup module and tests. It does not mount a webhook, enroll a purchase, advance coverage or permit retirement.

## Trusted normalized input

`observeTopupHistory(db, input, {enabled: true})` accepts exactly primitive event ID, live/test Boolean, payment ID, Checkout ID and captured existing purchase revision. No raw provider object is accepted. The future trusted caller must authenticate and validate its supported event schema and authoritatively associate the refund, dispute or charge with that exact payment/Checkout/mode. It captures the revision before those authoritative reads. Unsupported or incomplete association is not an observation and cannot receive coverage credit. This storage API does not perform provider verification.

Input values are copied before hashing. Payment/Checkout fingerprints reuse the existing mode-separated identity scheme. The receipt uses a distinct `history-event` domain plus mode and event ID. No raw IDs or event body are copied into new storage, output, logs or errors.

## Atomic storage boundary

One D1 batch inserts a new unlinked receipt at database UTC only when the exact granted purchase, mode-bound aliases, captured reconciliation revision, existing retention row and associated settled Checkout attempt all still match. The next statement increments that purchase's existing revision only when the insert changed one row. The following statement clears `resolved_at`, `resolved_zero_since` and `evidence_digest` only when that revision write changed one row. Credit balances, terminal flags, governing causes and existing `history_proven` are untouched.

Thus a same-status round trip starts a new observation and invalidates an old age or in-flight retirement/reconciliation capture. A duplicate event changes nothing. Before settlement, after deletion, under stale revision or mismatched association, no receipt is inserted. Those outcomes remain pending for later authoritative handling. Dense typed acknowledgements are required. Unknown committed outcomes return generic unavailable without retry or compensation.

Migration 0029 retains only `event_digest` and `observed_at`, with a cleanup index. There is no purchase/account foreign key or new association column. Account deletion erases its existing linked records while this unlinked receipt keeps deduplication only until approved cleanup. `cleanupTopupHistoryReceipts` is separately default-off, uses database UTC and deletes at most an explicit 1–256 rows at or beyond 30 days. Future daily maintenance must drain all due pages in its first successful run. Replayed old events after receipt expiry can conservatively invalidate age again, never grant credit.

## Boundaries and qualification

Coverage record, epoch enrollment/rotation, replay windows, event completeness and restore proof are deferred. Existing purchases and prior loss/unknown history do not become qualified through this API. Existing retirement and sales gates are unchanged, and automatic erasure remains off. No provider reads, financial disposition, quota, route, schedule, configuration, public wording or deployment is added.

Shared Node and actual local D1 fixtures cover concurrent duplicate and distinct events, mode/alias mismatch, settlement-before/after/race, unchanged-state observations, stale captures, genuine rollback, lost/malformed committed acknowledgements, account deletion ordering, nonterminal/mismatched attempts, retention-CAS invalidation, preservation of terminal/unknown flags and indexed bounded 30-day cleanup. Ordered/legacy parity adds one table and one index only. Final exact results are recorded in the PR. No public artifacts or golden changes, so screenshots are inapplicable.
