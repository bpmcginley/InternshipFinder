# P-2.1ax Follow confirmation and pending-request deletion

[#496](https://github.com/bpmcginley/InternshipFinder/pull/496) starts from exact main `8a8fbe74`. The approved Follow design requires an explicit confirmation action and a separate way to delete a pending request. The Worker now connects those existing storage operations to two bounded POST routes.

| Action | Credential | Response |
| --- | --- | --- |
| `POST /follows/confirm` | 101-byte confirmation bearer | 204 confirms the exact scope. 410 covers an unavailable confirmation, including an expired, replayed or wrong-purpose token. |
| `POST /follows/delete-request` | 104-byte `fd_` bearer | 204 covers deletion, replay and unknown credentials of the expected shape. The operation preserves other follows. |

The bearer goes in a `text/plain` body. Query parameters are rejected. Cookies and authorization headers do not grant access. GET and HEAD fall through to 404. Both operations recheck time after body admission and return empty no-store responses. Malformed input returns 400. The reader stops after five seconds or the route's byte bound. Four anonymous slots are shared per isolate and stay occupied until D1 settles. Timeout, saturation and storage failure return retryable 503 without logging request data or the storage error.

Local verification covers expired and concurrent confirmation, exact scope watermark, wrong-purpose and replayed credentials, deletion with a surviving confirmed scope, malformed and oversized bodies, scanner-safe methods, stream cancellation and capacity during a held database action. The original router-response fixture is preserved. Existing one-click unsubscribe is unchanged.

Signup, credential issuance, the first-party confirmation page, sending and Worker deployment remain separate. The eventual links and first-party pages must keep the bearer out of the request URL. No real data or provider was used.
