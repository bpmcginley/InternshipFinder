# P-2.2ae dormant top-up retirement

This package implements the approved 400-day resolved-zero retirement boundary for provable histories on #416. It adds no route, provider request, scheduler, public copy, configuration or activation. Exact changed user-visible strings: none.

## Provenance and eligibility

Migration `0020_topup_retirement_provenance.sql` adds `history_proven` and a nullable canonical `evidence_digest` on the existing cascading retention row. Both are non-identifying technical proofs. Existing rows default to unknown (`0`) and a missing digest, with their timestamps preserved. Creation dates and a clean later snapshot cannot repair missing history. The legacy schema mirrors the migrated shape.

New first settlements establish provenance from their complete verified evidence. Reconciliation preserves it across repeated clean observations and favorable hold release only when every prior governing hold is explicitly resolved or still retained. Discarded unresolved causes, unknown/inconsistent complete evidence, a missing previously confirmed full refund, and prior or newly observed loss block future erasure. Unknown stays unknown. The digest hashes the complete available verified association and lifecycle facts, including any supplied timestamps, with canonical object keys and refund/dispute ordering. Changed evidence resets resolution and zero age to database observation time even when the credit flags are unchanged. Only the digest is retained, never another raw reference list or payload. Canonical input must be plain JSON. Date objects, custom instances, accessors, sparse arrays and other unsupported values are rejected before cloning can erase their type. Explicit ISO timestamp strings remain distinct facts. Associated invalid evidence clears the old anchor. No extra account or provider identifiers are stored. A separate authoritative/manual history-resolution design is still needed for these blocked records.

## Trusted operation and transaction

`retireResolvedTopup(db, paymentHash, readFreshEvidence)` captures the purchase, revision, flags, fingerprints and exact retention timestamps and its exact associated settled checkout attempt in one read before invoking the trusted evidence reader. The attempt must match the shared supported pre-tax economics independently verified at settlement, currently 300 USD minor units for 25 runs. This is separate from the tax-inclusive captured purchase amount. Missing or mismatched attempts are unavailable. That callback must perform fresh complete authoritative reversal reads for the captured purchase, using the existing bounded provider readers and trusted offer/payment association. Cached snapshots, browser input and unverified webhooks are not valid inputs. This package never invokes a provider. Mode-domain fingerprints, payment/checkout identity, captured amount, currency and current complete financial resolution and exact fresh digest equality are checked again. Residual provider-side changes after the read still require the separate revision/reconciliation discipline.

Transport failure returns pending without changing evidence. Associated unresolved or inconsistent observations go through existing reconciliation CAS so a later cleanup cannot reuse an old age or forget a newly observed hold/loss. A newly observed terminal financial transition first invalidates the old anchor under the captured revision, then reconciles and starts a fresh conservative period. If reconciliation fails or loses the race, that earlier invalidation can only delay cleanup. No erasure occurs on this path.

For an eligible observation, one D1 batch changes the durable claim to `retired`, deletes the exact purchase and cascading allocations/reconciliation/retention, then deletes only its matching settled checkout attempt. The first update and both deletes fence the full captured immutable purchase and attempt tuples, including attempt id/owner/checkout/offer/pre-tax amount/units/currency/state/creation and purchase identity/economics/creation. The first update also rechecks the captured revision, exact retention timestamps, known history and the matching digest, current zero available-plus-held units and database UTC `now - 400 days`. It refuses any surviving linked legacy run or funded generation and any associated non-settled attempt. Subsequent writes depend on that update's transaction-local change count. No account, session, unrelated purchase, unrelated attempt or run is deleted. The retained claim has only payment fingerprint, checkout fingerprint and terminal state, so replay cannot grant again.

The ordered migration test proves old timestamps survive with unknown provenance, exact schema parity and rollback. Final local checks passed: 747 Node tests, 326 actual Workers tests, JavaScript lint, generated API check, whitespace check and startup payload report.

Independent review, CI and coordinated owner integration remain required. Migration0020 must precede retention-aware code deployment. The production provider adapter, scheduling, observed physical cleanup timing and manual resolution of unprovable histories remain separate. The existing verified reader supplies no provider lifecycle timestamps. A digest detects observed changes but cannot detect an unobserved transition back to identical facts, including an appeal round trip. It never proves continuous provider history. A future scheduler must establish the approved age with adequate authoritative event/history coverage and must not erase unprovable cases. Favorable dispute resolution remains eligible only with preserved prior causes and fresh complete proof. This is an explicit activation gate. No production migration, remote database operation, provider traffic, deployment or release occurred.
