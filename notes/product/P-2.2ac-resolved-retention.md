# P-2.2ac resolved-zero retention prerequisite

The approved #178/#226/#294 policy is 400 days after zero remaining units and financial resolution. This package records the necessary evidence and timestamps. It provides no retirement operation, sweep, scheduler or activation. Exact changed user-visible strings: none.

## Storage and transactions

Migration `0019_topup_retention_evidence.sql` and its legacy mirror add one purchase-keyed, cascading row: `resolved_at` and `resolved_zero_since`, both nullable UTC timestamps. There are no new account or provider identifiers. Existing purchases receive no backfill. Creation dates never establish resolution or zero time.

First settlement and reconciliation commit this row in the same guarded batch as their financial state and balances. Complete validated current refund/dispute lists establish resolution. Pending/requires-action refunds, inquiries, active disputes, appeals, missing or inconsistent evidence block it. A prior full-refund flag does not bypass this validation. Every still-known prior hold ID must appear with a terminal outcome. Older full-refund transitions discarded hold IDs, so this prerequisite records complete-current evidence but cannot prove those historical identities. That remains a separate erasure gate. An associated invalid snapshot clears existing timestamps only under its captured revision, without changing credit state. Stale captures cannot clear newer evidence.

A newly verified terminal loss may establish resolution in its first transaction. Existing reconciliation stores only a prior-loss Boolean and clears governing hold IDs on loss. A later lost object cannot prove that the governing lost outcome remains present. Every prior-loss refresh therefore blocks resolution pending a future authoritative governing-identity/manual-review boundary. This conservative limitation does not change credit policy or automatically restore lost units.

Repeated resolved evidence preserves the timestamps. A positive available-plus-held balance leaves `resolved_zero_since` null. All existing purchase debit/restoration paths update it explicitly in their transactions: reaching zero starts database UTC time, restored available or held units clear it, and a later return to zero starts again. These statements preserve exact D1 row-count and CAS checks. A trigger approach was rejected after actual D1 showed trigger writes would change those counts. Account deletion cascades the new row while existing terminal fingerprints survive.

## Remaining release boundary

A timestamp is not permission to erase. The next retirement package must obtain fresh complete authoritative evidence, capture the appropriate revision before reading, and atomically recheck zero balance, financial resolution, elapsed 400-day cutoff and revision before retiring durable fingerprints and removing the purchase, allocations and related account-linked records. It must handle restoration, new reconciliation, deletion and pending run callbacks racing cleanup. No expired period is inferred across a known unresolved transition.

A positive unresolved observation clears the anchor. A temporary provider transport failure proves neither resolution nor an unresolved financial event. Existing recovery can return early without reaching this storage helper. Such a failure must block erasure, require a fresh successful read, and must never advance an anchor or manufacture resolution. This package does not mount provider/recovery flows. Future scheduling, observed physical deletion timing and manual-loss evidence remain prerequisites to claiming retention enforcement. Migration0019 must precede a future deployment of these retention-aware writers. No production migration or deployment occurs here.
