# P-2.1a: dormant follow lifecycle

Bruce approved the recommended P-2.1 design decisions; this is the first storage implementation slice. **Worker merge still needs Bruce.** Nothing imports this module from the router or scheduler. No signup, email, policy publication or deployment is enabled, and no operating values have been invented.

`follows.js` accepts a trusted public catalog supplied by a future caller, validates company or field/state scopes, and stores a sorted, deduplicated JSON scope as the subscription key. It rejects arbitrary text, extra filters, unknown keys and the remote pseudo-state. Email normalization trims surrounding whitespace and lowercases the address; it does not merge dots or plus aliases. Multiple requests share one random subscriber ID but each scope needs confirmation. Repeating a request does not extend its pending retention.

Tokens are minted separately, for future dispatch-time use. D1 stores only a SHA-256 hash, random generation, purpose, scope, expiry and optional requested account hash. A random 256-bit secret remains only in the returned bearer value. Confirmation reissues replace the previous scope token; unsubscribe tokens stay valid until deletion. Reading a token cannot confirm. Explicit confirmation atomically confirms only its scope, applies the account linkage recorded in that token, and consumes it. An existing different linked account cannot be overwritten. The confirmation timestamp is the future matching watermark's starting point.

Unconfirmed scopes and requests expire after seven days; a delayed token cannot extend that period. Confirmed scopes remain until deletion. Unsubscribe uses its own token purpose and deletes the subscriber, all subscriptions and tokens through foreign-key cascades. Account deletion accepts only a trusted authenticated account hash and removes linked subscribers; this helper is not yet wired to `DELETE /me`. A transaction failure rolls back both linkage and token consumption. Deleted tokens cannot affect a later signup with a new subscriber ID.

Migration `0002_follow_lifecycle.sql` adds three tables and two indexes; the accepted baseline is untouched. The identical addition remains in legacy `schema.sql`. The reserved management purpose avoids a later SQLite table rebuild; no management helper is implemented here. Schema equivalence and lifecycle run against local D1 as well as SQLite.

**Deferred:** P-2.1b management/selective removal; bounded request controls and catalog delivery; outbox and dispatch; matching export; route/account-deletion integration; UI and disclosure. Before exposure, queued jobs must be deleted in the same transaction and the approved separate keyed daily marker must survive deletion only through the next UTC midnight. Preserve seven-day subscriber-linked outbox retention, 48-hour stale digest expiry, consent recheck and no retry after ambiguous provider acceptance. None of those sending records or paths exist in this slice.

Postal address, sender/domain onboarding, actual sending entitlement/quota, reserved capacity and shared attempt cap, secret provisioning and operator deployment remain required inputs. Tests use only synthetic records. No sender, provider, remote database, AI or publishing call is used.
