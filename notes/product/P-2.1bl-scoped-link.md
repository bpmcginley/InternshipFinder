# P-2.1bl: scoped linking through confirmation

Stacked on frozen #516 `09cb7f49`. This dormant slice implements the approved per-scope account choice through a request, queued intent, one claim, a confirmation token and the fresh transport fence. No route, signup admission, sender, public copy or activation changes.

`requestLinkedFollowConfirmation` accepts a trusted first-party session proof, never a request-supplied account identity. Every write and the receipt SELECT check the exact session hash/account and current SQL expiry inside one D1 transaction. Only the existing approved account hash enters the queue. Migration 0023 adds that nullable field and its deletion index, with legacy parity. No raw session or bearer is retained.

Equivalent live owner requests replay the same job. Conflicting anonymous/other-owner intent and already-linked scopes return no new job. An expired request can be explicitly renewed. Claim copies the exact queued owner to the token and the final transport fence checks both. Inbox confirmation remains the only operation that links the scope. A confirmed unlinked scope gets a fresh seven-day linkage window without changing its confirmation or watermark. Cancelling that request preserves the confirmed follow. Expiry clears its pending queue and tokens. General unsubscribe remains address-wide.

## Required next boundary

Linkage must not be exposed until atomic account deletion integration lands. The next package must build statements for removal of pending owner jobs/tokens and linked scopes, insert them into the existing `deleteUser` batch, and preserve unlinked scopes, their general unsubscribe capability and the independent daily marker. Existing payment guards must roll the entire deletion back. Confirm-before-delete removes the newly linked scope; delete-before-confirm invalidates the token. Claim-before-delete must fail its final fence, while delete-before-claim has no job. An already accepted message cannot be recalled. Current session validation fences a deletion that precedes a request, but this package does not claim the reverse ordering is integrated.

Activation also requires the existing bounded signup admission, canonical catalog, generic responses, deployed migration, approved UI/privacy and sender/configuration gates. No HTTP caller imports the new helper. This package does not authorize mail or production storage operations.
