# P-2.2u Verified top-up Checkout event handoff

The internal entry point accepts the event returned by the existing signature verifier. A Checkout ID already bound to a top-up stays in this boundary even when the top-up marker is missing. A reserved top-up marker and a durable Checkout ID may identify different attempts. Ambiguous or conflicting evidence yields `pending`. An `unclassified` result only means the lookup found no top-up association. The future router must still classify the event before selecting a billing path.

The stored attempt must match the signed object's Checkout ID, attempt ID, user reference, offer version, units and payment mode. The caller resolves trusted historical configuration by the stored offer version and the event's verified mode. The existing recovery path re-reads the provider over its bounded GET transport, then uses its revision and claim fences to settle or expire the attempt. The event's payment status and totals serve only as event data. The helper returns a generic outcome.

Completed, delayed-payment success, delayed-payment failure and expiration events can initiate this authoritative recovery. Exact terminal attempts and deleted attempts give an inactive result. The production router, verification receipt, charge and dispute routing, release and activation remain owner gates. [Stripe Checkout event types](https://docs.stripe.com/api/events/types)
