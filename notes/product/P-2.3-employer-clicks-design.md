# P-2.3 posting clicks per employer

2026-11-10. **needs-bruce: proposal only.** No policy, collection, implementation or deployment is approved. Earlier design-note merges do not authorize this package. No production analytics were read.

**Meaning and scope.** Count a person's activation of an organic posting link on the dashboard or generated internship pages, at most once per canonical company per page load. Repeated clicks, including different roles at that company, do not add another; reloads and separate tabs can. Keep the seen-company set only in page memory. Honor existing `nocount`, automated-browser and bot exclusions. Exclude sponsored boxes, widgets, email links, extension actions and Auto-Apply starts. This measures accepted browser signals, not unique people, applications or verified employer-site arrivals. Existing global posting clicks, paid-placement counts/reports, billing and payment rules remain unchanged.

**Exact proposed words.** Posting-link labels stay unchanged; no totals appear publicly. Admin heading: “Employer posting-link activations”. Columns: “Day (UTC)”, “Company”, “Count”. Explanation: “At most one organic posting-link activation per company per page load. Reloads can count again. These are not unique people, applications, or verified arrivals. Counts may omit blocked or dropped events.” Disabled: “Employer posting counts are off.” Empty: “No accepted posting-link activations in this period.”

Proposed privacy addition, **unapproved**: “We also count organic posting-link activations by employer and UTC day, once per employer per page load. Reloading can count again. The browser sends only a fixed event name and the employer's public key. We store only the day, employer key and total, never an account, visitor identifier, posting identifier, IP address, search or full URL. Our existing abuse check briefly holds the network address in memory; it is not saved. Daily totals are deleted after 90 days, without monthly rollups. Only the site owner can read these totals. Because they identify nobody, Delete my data cannot remove an individual's contribution. The existing nocount setting disables this counting.”

**Proposed contract.** Reuse `POST /hit` with a separately validated event/key branch and a separate aggregate table: `(day UTC, public_company_key, count)`, unique on day/key. Server supplies day and increments one atomically; reject client dates/counts and extra fields. Do not put company keys in existing event/page dimensions. Add a separate aggregate member to guarded `GET /admin/employer-metrics`, completed UTC days only, existing 1–90-day window and `no-store`; preserve every paid/funnel field and calculation. No public route, employer report or mailing in this package.

**Keys and bounds.** Reuse `seo_pages.employer_key`, never a browser reimplementation. Existing `data/roles/index.json` exposes keys but excludes non-purchasable roles; dashboard rows lack keys. Implementation therefore needs an approved public export mapping for all eligible organic employers, row/link annotations and golden review. Propose a worker-validated snapshot of at most 10,000 keys, each at most 200 UTF-8 bytes; unknown keys add nothing. Missing, oversized or invalid snapshots fail closed. Cache only a validated snapshot for a bounded lifetime approved before build. Proposed independent atomic caps: 1,000 accepted events/company/day and 50,000/day overall; existing origin/body/bot/minute checks remain. These bounds limit damage, not establish authenticity: public beacons can be forged.

**Retention, recovery and approval.** Daily cleanup removes rows older than 90 days; admin reads exclude expired rows. No rollup, identity linkage or historical backfill. Owner deletion removes an entire company/day range, not a person's clicks. Disable collection on retention failure; resume only after cleanup and snapshot validation, without replaying lost events. Bruce must approve wording, scope, mapping, caps, cache lifetime, retention/recovery and operator enablement. Remain off until privacy publication, reviewed worker/schema/client PRs and Bruce's deployment. Validate duplicate clicks, UTC boundaries, unknown keys, concurrent caps, cleanup, admin auth, opt-out and unchanged paid metrics with synthetic offline tests.
