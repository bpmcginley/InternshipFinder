# P-2.1cv dormant Follow delivery owner

This implements the dormant storage and recovery scope approved in [#563](https://github.com/bpmcginley/InternshipFinder/pull/563). The wrapper is unmounted and disabled by default. There is no route, schedule, provider configuration, reset, automatic reclaim or restore authorization.

## Ownership and continuation

Migration 0031 and its legacy schema mirror add one current private record with format version, random acquisition generation, phase, next queue kind and at most two job ID/expiry pairs. They add no recipient address, subscriber identity, message, raw token or provider response. Schema adoption seeds once and does not replace an existing record. Runtime never initializes a missing row.

The new owner module validates the bounded record, then acknowledges a ready-to-running compare-and-swap in the same D1 batch as its generation read. The new wrapper invokes the existing Follow link runtime only after that receipt. Two independently constructed wrappers share the same database fence. The existing final consent-to-transport path is unchanged.

A clean processed or capacity-paused result requires exact bounded counts, matching outer and dispatch status, a valid cleanup receipt and valid continuation. Nonzero uncertain or unavailable counts hold the generation, including a processed result with unavailable work. The exact freshly acquired send-free maintained result may return ready without writing cursors or next turn. Other no-dispatch results remain closed.

Lost acquisition acknowledgement never invokes delivery. A lost hold acknowledgement leaves running or held state closed. A lost acknowledgement after clean completion may mean ready already committed. The old caller stops and cannot retry or hold a successor. Tickets are opaque, single-use module-private WeakMap entries consumed before any completion await.

Deletion and ID/expiry replacement triggers redact only matching cursor references while preserving phase, generation and turn. Completion checks each referenced queue row and exact expiry in its update, so an active invocation cannot restore a deleted or replaced reference. Reads treat logically expired references as absent. Existing bounded management expiry can run separately while held and only its triggers alter obsolete references.

## Receipt compatibility

Actual native D1 includes trigger writes in `meta.changes`. Management expiry therefore uses a single transaction containing the existing indexed bounded DELETE and `SELECT changes()` to report only directly deleted jobs. The management request upsert returns at most one constant with `RETURNING 1 AS changed`. Anonymous rate and database-day checks and generic accepted/unavailable responses remain unchanged. There is no retry after an uncertain acknowledgement.

The test helper now faithfully returns DML RETURNING rows. Existing runtime observation fixtures account for the extra expiry scalar statement. No existing delivery runtime, dispatch, account deletion, routing, configuration, public API or provider source changes.

## Qualification

All data and transports are synthetic. Focused Node and actual local Workers/D1 tests cover concurrent acquisition and handoff, restart continuation and capacity pause, malformed state/results, lost acquisition/hold/completion acknowledgements, late provider acceptance, deletion/cascade/replacement races, maintained policy flip, cleanup under hold, direct counts with cursor triggers and unrelated parallel writes, legacy schema parity and idempotent adoption. Final exact results are recorded in the PR after the full suite completes.

Local SQL/runtime evidence does not establish production provider delivery, restore safety, shared provider capacity or scheduled operation. The new owner is not mounted anywhere. Existing Follow runtime callers remain unchanged until a separately reviewed integration replaces them.

## Remaining gates

A restored database can contain ready ownership and resurrect old claims or a lower budget. This package cannot independently detect that rollback. All sending must remain held after an unverified restore until separately approved anti-rollback and provider evidence exists. There is no reset API in this implementation. Adoption, mounting, cadence, provider capacity shared with order mail, sender/presentation values, production restore and any hold-release procedure remain separately gated. Cursor cleanup uses existing queue lifetime and adds no retention period.
