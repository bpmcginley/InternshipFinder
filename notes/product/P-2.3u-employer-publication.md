# P-2.3u optional employer publication adapter

Draft [#410](https://github.com/bpmcginley/InternshipFinder/pull/410) starts from exact published main `45ccdddaf7ad281d00fae6e54ec6d51657748d17`. The claim is the standalone publisher, new `site/employer_publication.py`, new focused tests, one exact catalog allowlist entry and own evidence/tracker. Refactor released these seams after #405. No workflow, data writer, Core/App graph, dashboard markup, browser activation or Worker configuration changes.

The explicit invocation is `python scripts/make_og_image.py --site SITE_DIR --employer-postings`, or the equivalent standalone `python -m internscout.site.publish SITE_DIR --employer-postings`. It is absent from every production workflow. The default path is unchanged. The existing `INTERNSCOUT_PUBLIC_DATA` selector chooses the already-staged export once; this package does not select a Git revision or establish export provenance. Each build requires a fresh unannotated export.

The adapter captures the manifest, every declared shard, first preview and majors exactly once from that selected root. Paths must be regular files, without symlinks/junctions. It calls the existing complete-export stage and exact PostingLinks validator, then requires the destination's staged inputs to match the captured source when the roots differ. Existing loader filtering/deduplication runs against a private copy of those captured bytes before any output write. Only after all validation succeeds are the annotated shard overlays, first preview and keys-only catalog written. The optional renderer binding and frozen loader input then drive the ordinary publisher, including highest-paying rows.

Missing shards, malformed/duplicate manifest JSON, inconsistent counts/preview, unsafe paths, malformed majors and mismatched staged inputs fail before writing. Filesystem write failures still fail the whole build: this is an artifact build gate, not a filesystem transaction or a claim that arbitrary concurrent input mutation can be made atomic. The upstream selected export must already be independently verified and stable. Publication must not proceed after a failed build.

The approved membership semantics are unchanged: include direct public postings from the complete declared export, including known Closed rows; use the existing canonical employer mapping. Generated eligibility/filtering still determines which rows render. No new private facts, identities, URLs in the catalog, duplicate validation rules or broader URL policy are introduced. Annotation affects only the previously approved organic shared listing and highest-paying links. Paid listings, Auto-Apply, widget/feed outputs, dashboard and digest examples remain unchanged. Browser capture remains off, and the catalog is admitted by one exact public allowlist pattern.
