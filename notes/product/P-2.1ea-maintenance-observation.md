The actual maintenance branch still uses the original single `waitUntil(runFollowScheduledMaintenance(...))` path when no usable observation port is provided. Off or unknown events never read the observation port. Malformed or throwing port configuration falls back to ordinary maintenance; it cannot turn maintenance off. All other scheduled branches are unchanged.

Optional integration requires a trusted `FOLLOW_MAINTENANCE_OBSERVATION` binding exposing `record(aggregate)`, and an explicit `FOLLOW_MAINTENANCE_OBSERVATION_TIMEOUT_MS` decimal string from 1 through 30,000 without padding. Neither binding nor value is configured here. The upper bound is a technical wait ceiling, not a selected production timeout or cadence. Binding identity and method are captured once. The trusted recorder must initiate promptly and return without blocking; timers cannot preempt arbitrary synchronous code. No sink implementation, credentials, destination, logs or retention policy is added.

`measureFollowScheduledMaintenance` uses the existing scheduler and returns an ephemeral `{result,observation}`. The original public scheduler API and status contract remain intact. A private counter increments at each actual underlying `.all()` or `.batch()` invocation, including thrown/rejected/lost-acknowledgement attempts. It does not count prepared statements, reserved budget or SQL statements within a batch, and does not claim that mutations committed. Bound statement calls remain wrapped. A separate monotonic start/end sample yields elapsed milliseconds rounded upward; late completion may exceed the maintenance deadline. Invalid or backward measurement suppresses observation without altering maintenance. No unknown duration is reported as zero.

When the optional port is valid, the first `waitUntil` resolves with the maintenance result independently. A second attaches recording only after maintenance settles and uses the existing #628 strict adapter, which passes exactly frozen `{status,durationMs,d1Calls}`. No identity, cursor, query, policy, error, provider result or free-form detail reaches the recorder. Only `pass-complete`, `partial` and `unavailable` are valid outcomes; actual D1 calls cannot exceed the scheduler's 48-call ceiling.

The second wait races only recorder completion against its explicit bound. A hanging recorder cannot keep that wait pending indefinitely; maintenance is never raced, cancelled, retried or relabelled. A late recorder is still observed for rejection, but is not recalled or retried, and its eventual side effect is not claimed to have been cancelled. Callback fulfillment does not prove durable recording or retention coverage. No observer runs inside a mutation, admission, delivery or final transport fence.

Native tests cover the actual entry's default/off/unknown behavior, invalid policy with honest zero-call unavailable, exact aggregate/frozen fields and independently counted bound reads/batches, partial and lost-acknowledgement results, late duration and broken measurement, pending/throwing/rejected/late-rejected recorders, and capture-before-await with recording strictly after work. The existing scheduler, #628 strict adapter and scheduled link tests remain regression gates.
