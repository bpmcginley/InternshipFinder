## Input and output boundary

`decideTopup` consumes normalized current data: captured amount including charged tax in integer minor units, currency, explicit refund/dispute completeness flags, and lists of `{id, status, amount, currency}`. The trusted future adapter must verify signature, purchase/charge/account association, actual paid status, currency and complete pagination/current objects; these supplied flags do not establish provider authenticity. No private provider identifiers are used in tests.

`previous` supplies committed deletion/full-refund/prior-loss/held booleans and the IDs of every dispute governing a prior hold. Held IDs must be consistent with the held flag. Identical duplicate current records count once; inconsistent versions of one ID, unsupported statuses, currency mismatches, invalid amounts and successful totals above the captured amount require reconciliation. No event ordering or provider API choice is made here.

The result classifies unused purchase units as `available`, `held`, `revoked`, or `retry`. It is not a grant or balance update. Non-retry results also report sticky loss/full-refund facts, the next governing held IDs and whether restoration needs manual review. `available` may release eligible held units but must never recreate consumed/revoked units or reset the grant ceiling. `retry` has no proposed state: retain the last verified allocation and authorize neither release nor a new grant. Trusted durable deletion/full-refund/loss facts remain terminal even if fresh reads are unavailable. `manualReview` is a restoration gate, never an instruction to automatically open a case on each replay.

## Approved decisions and review correction

Only distinct successful refunds count; partial and pending/failed/canceled/requires-action refunds do not revoke. Full refund and deletion precede release; loss precedes an active hold. Every approved formal/appeal active status holds all unused units even for a partial monetary dispute. Inquiry statuses alone do not create a hold. A later favorable outcome cannot undo prior loss automatically.

Release requires each governing prior dispute to be present and favorable, with no other active/lost/terminal blocker. Missing or inquiry-only governing disputes retry even alongside an unrelated favorable or newly active dispute. This prevents an unrelated old win from releasing a hold, or a new active dispute from replacing unresolved prior identity. Only after all prior IDs are validated can the next held-ID set contain current active disputes alone. Independent review identified this case before freezing; regressions cover both paths.

The future reconciler must serialize per purchase and atomically commit the decision, governing identities, sticky facts, balances/allocations and durable receipt using a revision/conditional write; conflict requires a fresh read. This module does not implement that layer, retention/financial-resolution decisions, provider retrieval, checkout, deletion fencing or admission. No live enabling follows from its presence.
