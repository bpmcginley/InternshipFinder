The new-sales capability requires an explicit private `STRIPE_TOPUP_MODE` of `test` or `live`, with no default. It also requires a nonempty primitive webhook signing key made of printable non-space ASCII. This local check establishes configuration presence and shape. Release still requires independent verification of the exact Stripe account, Price, endpoint, signing secret and delivered events.

The dashboard hint and offer use the same sales gate. Checkout retains its existing Origin and session checks. The adapter checks the Price against the captured mode before it allows a new attempt, then uses that mode for create and open responses. The provider key, signing key, Price, mode, Managed Payments choice and site root must still match after Price verification and at adapter admission and provider invocation. The existing final authentication and database checks are followed by a fresh synchronous capability check before returning the offer or a hosted URL.

A settings change before reservation closes the request. A change after a creating attempt has committed prevents a new provider POST and preserves the pending recovery barrier. If the POST was already sent, a verified response can still attach the checkout ID for durable recovery. The invalidated adapter does not expose its URL or issue another POST. The normal signed and attached historical recovery paths are independent of this new-sales check.

Historical settlement uses the verified signed event's mode. Purchased balances aggregate per user without a Stripe-mode filter. A test-mode deployment must use a separate Worker and D1 environment and signing endpoint. The live sales release requires the intended live mode and verified live configuration. This package adds no configuration values or production activation.

Seven new shared scenarios cover absent and invalid settings with zero provider calls, Checkout Origin and session ordering, mismatch in either mode with only one Price GET per route, valid-to-valid settings changes during Price and after the account read, an admitted attempt without POST when configuration changes at reservation, final authentication and readback races, and valid live-mode checkout. Existing valid test-mode and sales-off signed historical recovery remain covered.
