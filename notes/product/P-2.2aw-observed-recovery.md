# P-2.2aw dormant observed reversal recovery

Draft [#571](https://github.com/bpmcginley/InternshipFinder/pull/571), based on exact main `8bd7a5b2`. Adds an optional trusted `historyPolicy` argument to the existing `applyEvent` / `applyFresh` / `topupWebhook` path. The production index still omits it. No environment flag, route or configuration enables this package.

Only literal `enabled: true` selects the new path. Mode and the bounded own-data version list are snapshotted; invalid policy holds a known granted purchase. Unrelated classification and terminal fingerprints retain existing behavior. The tiny existing family lookup moves to a pure module to avoid an import cycle, with the old named export preserved.

After the existing verified event classification, granted purchase and historical offer checks, the exact associated event passes through #568 once. Only `observed` or freshly verified `duplicate` permits calling the unchanged full recovery helper. That helper captures a new revision and performs new payment and complete reversal reads. A history receipt never acknowledges billing success or substitutes for monetary verification. Pending, unavailable and uncertain committed observations return the existing retry outcome, which releases the existing `stripe_events` preclaim. There is no automatic retry within the invocation.

The authenticated event, explicit enabled/disabled policy and invocation-scoped primitive provider key/Price snapshot are captured synchronously before the billing receipt await. The pinned configuration is supplied only to the opted-in top-up branch, leaving ordinary billing on its original environment. Direct top-up callers capture the event before optional discovery and reused through observation and fresh recovery. Trusted offer and policy snapshots cannot change after an awaited phase. History admission keeps its existing deadline/stream bounds and non-cancellable admitted D1 semantics; full recovery keeps its separate existing reader bounds. This package does not claim one global deadline across both operations.

Synthetic signed tests call the real `verifyWebhook` and `applyEvent` receipt path with the explicit trusted policy. The actual HTTP route remains default-off and its existing suites remain unchanged. Tests prove default caller parity, signature rejection, observation revision 1 then fresh recovery revision 2, provider state changed after the observation commit, successful replay, history receipt plus failed recovery/retry, committed lost acknowledgement, deletion/revision races, terminal handling and no unrelated employer/subscription fallthrough. A synthetic key/Price mutation immediately after #548 and policy mutation during discovery leave both phases pinned. Signed/native regressions also mutate the verified event during discovery and flip enabled or disabled policy during receipt acquisition; the original event digest and admission choice remain fixed. Invalid enabled policies remain pending. Node and actual local D1 counts are recorded in the PR.

No new storage, coverage advance/enrollment, retention authorization, monetary policy, provider credentials/settings, actual Stripe request, deployment or activation. Future release still requires a trusted supported mode/schema policy, receipt maintenance and independent coverage/restore qualification. Needs independent exact review and Bruce release.
