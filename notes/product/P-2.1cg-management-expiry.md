# P-2.1cg Bounded management request expiry

[#546](https://github.com/bpmcginley/InternshipFinder/pull/546) starts on exact main `4c13e63c`. It adds only `expireFollowManagementRequests` to the existing retention module, shared scenarios and this note. Existing bulk retention source and behavior are unchanged. The lead explicitly reserved shared STATUS for separate updates; no registry or wrapper edit is needed because both existing retention wrappers discover exported scenarios.

The helper requires literal enabled=true and an explicit positive safe-integer maxRows. Disabled or invalid options cause zero D1 access. One DELETE selects at most that many expired rows through the existing migration0026 covering expiry index, ordered by expires_at and rowid. SQLite UTC is evaluated in that same statement, including expiration equality; there is no caller clock, prior read, pagination cursor, loop or race between selecting and deleting. Claimed and unclaimed expired jobs are eligible. Live jobs, credentials, subscribers, follows, daily digest markers and budgets are untouched. Existing migrations0026/0027 suffice; no schema change or retained field is added.

Only literal successful receipts with empty results and a safe nonnegative change count at most maxRows establish completion. A failure, malformed receipt or lost acknowledgement returns generic unavailable with no retry, refund or assumed deletion count. A database failure rolls back the entire DELETE. The result contains only status and the verified aggregate removed count.

Five new shared scenarios cover disabled/invalid no-I/O, claimed/unclaimed expiry and stable ties, preservation of live claimed/unclaimed rows and credentials/budgets, malformed or genuinely committed-but-lost acknowledgements, and trigger-induced atomic rollback. An additional 20,000-row synthetic backlog is part of those five scenarios: deleting seven leaves 19,993, with actual local Node SQLite and Workers/D1 query plans using the covering expiry index and no temporary ordering B-tree. These are synthetic qualification counts, not production measurements. All four pre-existing retention scenarios remain unchanged. Nine focused Node and nine actual local Workers/D1 cases pass; two full registered Node runs each passed 911/912, with different unchanged native checkpoint failures recorded in the PR. The first standalone R2 failure passed its exact isolated rerun; no unrelated fixture or runtime was edited. Hosted checks and independent review remain required. Pinned ESLint/Prettier, generated API and whitespace checks pass.

This removes expired rows from the current table only; it makes no claim about provider backups or recovery retention. The caller still needs an explicitly qualified scheduling frequency and batch cap to keep up with expiry, plus request TTL/re-request and provider/rollout qualification. There is no scheduler, router, configuration, provider action, sending, public copy or activation. Public assets and golden outputs are unchanged.
