# P-2.1dw bounded archive enqueue release

Draft #630, based on `c40f8a57e3b30d3c34c8dfe1cac6cba9a478bc6b`. Owns only `worker/src/follow-archive-release.js`, `worker/test-workers/follow-archive-release.test.js` and this note. No core enqueue, entry, scheduler, schema, migration, settings, public output or sending changes.

## Contract

`runFollowArchiveRelease(options)` is disabled unless `enabled === true`. Enabled callers explicitly supply `db`, authenticated first-party `fetch`, catalog authority accepted by `prepareFollowCatalogRelease`, archive `indexUrl/indexSha256/bounds`, matching `limits`, `maxProgressBytes`, `maxPendingBytes`, and `budget`. Optional synchronous `now` and `monotonicNow` ports support deterministic qualification. This module does not establish deployment authority for supplied pins or previous valid keys.

The budget requires `maxPages`, `pageSize`, `maxSubscribers`, `maxD1Calls`, `maxStatements`, `maxFetches` and `deadlineMs`. Technical ceilings are 128 pages, page size and total subscribers, 48 binding calls, 100 SQL statements, 257 GETs, and the existing positive signed timer ceiling. These are maximum representations for this dormant contract, not production cadence, load or quota choices. Matching and archive byte/object limits remain explicit existing inputs.

The runner snapshots policy records and binding methods before awaiting. It loads one digest-pinned catalog with the existing loader/parser, preserving independently supplied previous valid-key continuity, and matches against `valid`, including keys no longer offered for signup. Archive authority requires the exact first-party `/data/follows/index.json` URL and an explicit SHA-256 pin. Each nonempty page reuses the existing reader to verify the same pinned manifest and its digest-addressed latest snapshot. Repeated GETs cannot select a newer manifest midway through this pass. No new cache, parser, snapshot producer or per-subscriber state machine is introduced.

All pages are sequential within one invocation. The internal subscriber cursor never leaves it or persists. Results contain only `status`, acknowledged `pages/subscribers`, attempted `d1Calls/statements/fetchCalls`, and aggregate existing enqueue outcomes. `pass-complete` means enumeration ended with qualified acknowledged outcomes in this invocation. It is not a stable database snapshot, delivery, provider coverage, or a release-health assertion. Conflicting, invalid or uncovered subscribers make the result `partial`. Known remaining capacity insufficient for another whole page also returns `partial`; uncertainty returns `unavailable` without a continuation or retry. Already acknowledged earlier pages may have committed before a later failure.

## Work and time bounds

Before each page, reserve its worst case: two fixed statements/calls for enumeration and final database UTC, plus two calls and five statements per subscriber (one bounded progress read and a guarded four-statement queue batch). The existing empty-window path costs less. Reserve two GETs per nonempty archive page after the catalog GET. The runner counts actual calls/statements and checks again immediately before invoking them. This does not bound arbitrary provider or D1 execution latency.

A single nonregressing wall plus monotonic elapsed deadline spans catalog loading and every archive page, clipped to the catalog release expiry. Remaining network timers are reduced for each read. Existing archive generated/enqueue/day SQL predicates remain unchanged. Each enqueue batch additionally starts with the existing migration 0025 `follow_catalog_admissions` empty-view guard, using the earlier catalog/common deadline cutoff. Database UTC checks this before any mutation. Its exact successful zero-change/empty-results receipt is validated and removed before returning the original receipts to the unchanged enqueue helper. Missing, expired or malformed guard fails closed. Once admitted, the transaction completes atomically; the deadline cannot cancel or prove absence of an admitted D1 commit. A late or lost acknowledgement never authorizes another page. Dense own-data success/change/result receipts are copied once before use. No-match UPDATE receipts require an empty result and a bounded change count. Queue INSERT/pending receipts require coherent zero-or-one writes; a new queue write must return its exact captured UUID, while an idempotent existing-job read must return one correctly shaped UUID. The SELECT has zero changes. A genuine zero-row CAS is partial, while malformed, sparse, contradictory or ambiguous receipts are unavailable even after a physical commit. Neither outcome retries or exposes a cursor.

## Pass and rollout limitations

There is deliberately no cross-invocation continuation. A capped pass starts again from the first subscriber next time. Native evidence demonstrates that repeated one-page invocations revisit the same first subscriber and leave later subscribers untouched. Repeated partial invocations therefore do not prove fairness or complete retention/matching coverage. A fresh pass also sees keys inserted behind a prior invocation's cursor. Production activation requires demonstrated complete-pass capacity under expected backlog and restart/insertion behavior, or a separately approved continuation design. This package adds no scheduler state or policy.

The qualified release, original coverage and enqueue cutoffs are not extended. Missing prior keys, a changed manifest pin, expired release, clock rollback, invalid receipt or unavailable archive keeps new work closed. No delivery or owner acquisition occurs, and no raw subscriber ID, email, scope, capability, snapshot bytes or cursor is returned or logged. Writer/archive publication, retained first-party artifacts, source authority, runtime migration adoption, G3, provider/restore evidence and actual scheduling remain separate launch gates described in P-2.1dc.
