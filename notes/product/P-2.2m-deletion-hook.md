# P-2.2m top-up account-deletion hook

[PR #303](https://github.com/bpmcginley/InternshipFinder/pull/303), stacked on frozen #299 `0d01aeb9`. Needs Bruce for merge and deployment. Migration `0015` is reserved; follow package #302 owns `0016`.

Owns migration `0015_topup_account_deletion.sql`, its legacy `worker/schema.sql` mirror, focused shared SQLite/local D1 tests and registration, migration equivalence assertions, and this package's tracker entries. No route, authentication, provider, billing or limits source changes.

The existing `deleteUser` transaction inserts/upserts `forget` before removing sessions (`limits.js:525`). The `BEFORE INSERT` hook rejects unresolved creating/open top-up attempts with internal `topup_payment_pending`, terminalizes only linked granted claims, and removes purchases with their allocation/reconciliation children plus resolved attempts with revision children. Existing deleted/retired claims remain terminal. No retained fields are added: surviving financial claims contain only the existing irreversible payment/checkout fingerprints and state, without account linkage, raw references, balances or timestamps. The approved indefinite replay-barrier retention is unchanged. Expired attempts without purchases do not gain a new retained record.

Preflight found one production forget writer across current main and all open branch sources: account deletion's INSERT/UPSERT. The hook runs even on its existing-row conflict path; it does not modify the target forget row or depend on NEW.rowid. Monthly cleanup's DELETE (`limits.js:574`) does not invoke it and retains the existing monthly-accounting behavior. Future code must preserve this meaning of a forget INSERT; direct UPDATE is not a deletion API. The legacy schema mirror installs the same trigger for the current operator migration-adoption boundary.

Reservation and deletion serialize in D1. If reservation commits first, its unresolved row blocks deletion and rolls back earlier account writes. If deletion commits first, the same batch removes sessions, so the fenced reservation cannot insert, disclose an attempt or call its adapter. Resolved attempt removal cascades its revision fence; old captured settlement cannot match the removed attempt, and retained claims block paid replay. Unknown creation never becomes deletable merely because time passed. Concurrent sign-out remains supported independently.

Validation: baseline17 targeted tests passed before edits. Final Node448/448 and full actual local Workers52/52 passed, including five new shared scenarios and migration/legacy schema equivalence (same53 tables/28 indexes, one new trigger). Tests cover fresh and conflicting UPSERT with both active states, rollback of earlier demand/usage writes, selective cascades and unrelated-account preservation, exact retained claim columns, replay after deletion, retired-claim preservation, repeated deletion, injected later session-delete failure restoring every financial/account row, actual monthly cleanup, both serial reservation/deletion orders and concurrent contenders. The older session-reservation test now expects active-checkout deletion refusal, while still testing independent sign-out and deletion-before-reservation. Its production source is unchanged. JavaScript lint, owned-file formatting and diff checks pass. External disposable preflight also passed nine SQLite and nine actual local D1 scenario groups. All data and provider adapters were synthetic; no live calls.

Dependencies remain #297's session-copy race fix, using the fenced reservation path for future public top-up requests, route mapping of the unresolved-payment error to an appropriate pending response, and owner-controlled migration adoption/deployment. Existing subscription/recovery checks and DELETE /me responses remain unchanged; this PR does not add a public top-up endpoint. The trigger takes effect when its schema is adopted, but top-up purchase/reservation production wiring remains absent. This hook does not make the later separate `deletePlan` calls part of the account deletion transaction. An explicit deletion-statement builder could replace the hook later if forget gains another meaning, but splitting financial deletion into a separate call would lose atomicity. No visible strings, screenshots or startup assets change. Public assets, data and golden fixtures are unchanged.

Semantics checked against [SQLite triggers](https://www.sqlite.org/lang_createtrigger.html) and [D1 batch transactions](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), with the UPSERT and rollback behavior verified in the actual local D1 runtime.
