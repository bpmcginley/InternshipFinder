# P-2.2au dormant history event association

Draft [#565](https://github.com/bpmcginley/InternshipFinder/pull/565), based on exact main `430c0872`. Implements the next observation step in approved [P-2.2am](P-2.2am-topup-history-design.md). No entry, webhook, replay traversal, schema or configuration is mounted or changed.

`observeVerifiedTopupEvent` is off unless explicitly enabled. The trusted caller supplies an already authenticated, bounded parsed event, its account-bound mode, supported historical API versions, historical offer resolver and injected transport. This is not a public JSON parser or signature verifier. Unsupported families/schema, ambiguous context or missing association stay pending. No default transport or credentials are selected.

The existing reversal event-family lookup is reused. A missing payment reference permits one bounded Charge discovery read. Discovery only selects a candidate. The coordinator then uses the extracted read-only portion of `recoverTopupPurchase`: exact purchase revision capture, settled-attempt and mode-domain fingerprints, fresh payment evidence, and fresh complete reversal evidence. The old recovery caller still performs its original reconciliation after those checks.

Only an exact verified Charge association and, for refund/dispute events, membership of the exact object ID in the respective complete list allow the existing observation transaction once. Event status and totals never change runs. Observed/duplicate/pending/unavailable retain their existing meaning. Missing or not-yet-settled purchases get no irreversible receipt. Retained deleted/retired fingerprints are inactive. Neither inactive nor unsupported results establish interval coverage or historical irrelevance.

One shared absolute deadline uses the existing payment-reader maximum of 10 seconds, optionally shortened. The request ceiling is one discovery plus the existing three payment and eighteen reversal requests. Existing phase body/aggregate limits remain; the owner forwards streamed bytes without buffering and cancels locked or late responses. Only exact URL, nonredirected status-200 responses pass. The absolute provider/read deadline also fences lookup and resolver completion and is checked immediately before invoking observation. It bounds the returned result, not the lifetime of an admitted D1 write. Once observation is invoked, its hashing and eventual batch/acknowledgement cannot be cancelled by this deadline. That write may commit after timeout, but no retry or late success is returned. Its durable receipt makes later independently verified replay safe.

Synthetic shared Node/native D1 cases cover all three object families, exact replay and new event IDs, discovery before capture, missing/crossed references, unsupported schema/mode/context, deletion and revision races, rollback, commit-then-throw acknowledgement, non-success/redirect/metadata errors, late fetch and stalled body cancellation. Existing purchase-recovery and observation suites run unchanged. Exact counts are in the PR.

Still required: trusted account/schema selection, complete interval event classification and traversal composition, receipt maintenance, coverage enrollment/restore qualification and separately reviewed retirement wiring. This module neither advances coverage nor changes balances. A future financial refresh must recapture and reverify after observation. No raw provider payload/reference is persisted here, no public wording or policy changes, no real provider calls, settings, deployment or activation. Draft remains needs-bruce pending independent review.
