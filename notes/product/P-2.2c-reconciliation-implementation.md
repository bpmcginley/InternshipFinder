## Storage and transaction

Migration 0005 and its equivalent legacy-schema append add one purchase-linked `topup_reconciliations` row: revision, sticky loss/full-refund flags and a JSON array of verified governing dispute IDs. These fields were approved. No person identifiers or provider snapshot fields beyond the approved governing dispute IDs are added. The row cascades with purchase deletion; durable payment/checkout replay claims remain separate and untouched. Parent modules and migrations 0001-0004 remain byte-identical.

`readTopupRevision` is read-only: an existing active purchase without reconciliation state has revision zero. Missing purchases and terminal claims are unavailable. `reconcileExistingTopup` requires the captured revision and exact immutable checkout/payment references, captured amount and currency to match the database. Prior loss/full-refund flags and governing holds come only from committed state, overriding any caller-supplied previous state. Orphan held units with no governing identities retry. Governing hold IDs remain meaningful when all units have already been consumed.

One D1 batch conditionally inserts/updates state at the expected revision, then moves only this purchase's current SQL `available + held` units, guarded by the immediately preceding statement's `changes()`. A losing contender cannot modify balances or hold IDs. Transfers preserve consumption and previous revocations; SQL conservation constraints remain active. Sticky terminal flags cannot regress. Any balance-write error rolls back the state change. Retry/stale/unavailable outcomes do not grant or recreate a purchase; database errors propagate without a partial commit.

## Integration requirements

Capture revision **before** authoritative provider reads. The trusted adapter still must validate signature, charge/payment/checkout/account association, paid status, offer and complete current refund/dispute data. Matching references here is an additional guard, not provider authentication. After a conflict, obtain a new capture and new provider reads; never reuse an old snapshot under a later revision. All financial state writers must participate in the same revision protocol. Event receipts and the eventual transport/router path are not implemented here.

Refund-before-grant and durable checkout recovery, exact per-run allocation/restoration, account deletion fences and operator publication/deployment remain prerequisites. Tests use raw SQL fixtures to model consumption/restoration and deletion between read and CAS; they do not claim those APIs are shipped. Retention still follows the approved purchase schedule: positive balance until deletion, otherwise 400 days after zero balance and financial resolution, with terminal reference fingerprints retained indefinitely. Resolution timestamps, cleanup and unresolved-dispute retention enforcement remain future work; this state row alone cannot authorize cleanup.
