# P-2.2am Payment history evidence for top-up cleanup

The approved policy removes eligible purchase records after 400 days with zero runs and no unresolved payment issue. The current cleanup coordinator can check a fresh financial snapshot, the purchase revision and the database cutoff. A dispute can return to the same status between two snapshots, leaving that check unable to prove the intervening history. Automatic cleanup remains off. [Approved refund and dispute terms](https://github.com/bpmcginley/InternshipFinder/pull/226) · [Approved run lifecycle](https://github.com/bpmcginley/InternshipFinder/pull/294) · [Existing cleanup](P-2.2ae-topup-retirement.md)

## Proposed proof

1. Establish a coverage epoch for the trusted Stripe mode and supported event schema before enrolling new purchases. An existing purchase or one whose first settlement races an incomplete collection window stays unproven. Keep the purchase pending when the necessary starting history cannot be recovered.
2. After verifying and associating a refund, charge or dispute event, record its observation and invalidate the affected purchase's cleanup age in one transaction before refreshing current state. Use the event identity for deduplication and database observation time for the reset. Reuse the existing purchase revision. Only the existing verified provider reads and reconciliation can change runs. A prior loss, unknown history or an unsupported event keeps cleanup blocked.
3. Backfill overlapping, fixed windows within the Stripe replay period. Validate mode, event shape, association and complete bounded pagination. Commit coverage only after every relevant event in the interval has been handled or conclusively classified. Retries, equal timestamps and provider errors cannot advance an incomplete window. Stripe exposes 30 days of Events history, does not guarantee delivery order and documents rare event generation failures in its public-preview recovery guidance. Confirm the coverage applicable to this integration before relying on any interval for erasure. [List Events](https://docs.stripe.com/api/events/list) · [Delivery order](https://docs.stripe.com/webhooks#event-ordering) · [Event generation failures](https://docs.stripe.com/events/manage-webhook-endpoints#event-generation-failures)
4. Require a current qualified epoch and coverage revision through the erasure decision, a fresh authoritative provider read and the existing atomic retirement fences. A new event, coverage fault or uncertain restore holds the record. A gap older than the available replay period remains unproven unless independent authoritative history can repair it.

## Storage and release

Keep one private current coverage record per mode with the opaque epoch, supported event schema, UTC coverage bounds, revision and health state. Replace it on rotation. A purchase retains only its nullable coverage epoch under the existing retention row and cascade. A separate unlinked receipt stores the event ID digest and observation time so its commit can be atomic with invalidation. Delete it in the first successful daily event cleanup after it reaches 30 days. Store no raw event bodies, new payment references, contact fields or account identifiers. No visible wording changes.

First qualify the default-off observation transaction with actual D1 tests for duplicates, same-status round trips, settlement races, rollback and account deletion. Separately qualify bounded replay and coverage, then verify provider event completeness, restore handling and the retirement scheduler before enabling erasure or using this as a top-up launch prerequisite. Provider or operator evidence that cannot establish continuity leaves the existing approved pending behavior in effect.
