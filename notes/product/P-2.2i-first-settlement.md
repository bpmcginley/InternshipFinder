Migration 0013 adds only an existing attempt reference and bounded integer revision, mirrored in the legacy schema while operator migration adoption remains pending. `captureTopupSettlement` increments the durable revision and returns the attempt tuple in the same transaction before either authoritative provider read. A newer capture invalidates older evidence even if its own read fails. Revision exhaustion fails closed. Never retry old evidence under a new capture, delete/reset an active fence, reuse an attempt ID, or reopen a terminal attempt. The fence is consumed only after terminal settlement, without another increment; deleting an attempt cascades its fence.

`settleFirstTopup` accepts trusted internal payment/reversal evidence, not request fields or redirects. It checks exact account, offer, pre-tax amount, units, checkout/payment/Charge IDs, live/test mode, currency and tax-inclusive captured amount. The reversal reader now returns its already verified Charge ID/mode so the boundary can compare them; no new storage or provider request is added. The ledger reference-hash helper is exported unchanged to retain its canonical live/test domains. Purchase creation time is captured before asynchronous hashing.

The first claim insert checks captured revision, state, nullable checkout ID and every immutable attempt field inside SQL. Unique payment/checkout fingerprints reject crossed aliases and terminal claims. In one D1 batch, each write is gated by the preceding `changes()`: claim, purchase initialized directly as available/held/revoked, reconciliation revision1 with terminal flags/governing holds, settled attempt, consumed capture. No temporarily spendable grant precedes a hold/refund. Consumed units start at zero; conservation and all prior replay barriers remain. Constraint errors roll back the entire transaction. Replays/stale captures return stale without balance mutation; existing purchases use the separate reconciliation path after fresh capture/read.
