# P-2.1ak Detached follow writer checkpoint orchestration

One writer attempt loads the private store and verifies the accepted record against independently attested immutable predecessor bytes through #365. It verifies any pending record against the exact local Git candidate through #372 and requires the same coverage boundary. Matched rows with predecessor proof must retain the exact carried timestamp and proof, including closed rows. Matching uses the exporter's ID-first and raw-URL fallback rules. A row genuinely absent from the candidate has no carry requirement. An explicit forward-seed attestation is allowed only when the store reports never seeded. Expired, unavailable or unexplained Git advancement holds follow coverage.

Stage consumes a verified no-pending read and submits the exact #372 bytes once. Only a timely named acknowledgement returns the pending generation. Recovery consumes a verified pending read. When the independently observed Git tip is still the predecessor, recovery holds the pending record without a write. A later observed tip must pass the caller's isolated #348 binder and #378 typed promotion checks. Recovery makes at most one CAS call. A subsequent attempt must reload and verify the accepted record before using its lineage. Ambiguous mutations, late replies and stale CAS results do not trigger a retry or cleanup.

The explicit absolute monotonic deadline is checked before and after blocking boundaries. UTC checks mirror the Worker's millisecond admission and exclusive expiry bounds before and after mutation replies and reject a clock sample below the attempt's highest earlier sample. Pending and accepted lifetimes are 24 hours and seven days respectively, as Bruce approved in #358. The module cannot cancel a blocking Git or network operation. Future writer integration must enforce a hard outer runner/process deadline, provide independently verified source bytes and accepted observation, call stage after immutable candidate commit and before push, and recover only after re-observing accepted Git. Definitive rejection remains a separate explicit operator action through the existing exact-generation client. No live writer, workflow, publication, credential or provider changes are included.
