# P-2.2l dormant session-fenced reservation

[PR #299](https://github.com/bpmcginley/InternshipFinder/pull/299), stacked on frozen #293 0b175257. **Needs Bruce for merge; no activation.** No schema or new retained identity is introduced.

`reserveSessionTopupCheckout` is a new dormant entry point for future top-up routes. It requires a strictly shaped first-party iss_ bearer and expected authenticated account hash. SHA-256 matches the existing sessions table; the digest is transient, never placed on checkout rows, returned to the client or passed to the provider adapter. After hashing, an injected/default clock is sampled immediately before transaction construction.

Both the initial checkout INSERT and active-attempt SELECT require the same stored session hash, account and unexpired row inside one D1 batch. Invalid, unknown, wrong-account, expired or deleted bearers cannot create or read an attempt or invoke the adapter. Concurrent valid calls retain one active attempt and only the winning insert invokes creation. The existing `reserveTopupCheckout` signature remains a trusted internal path; both entry points share the same offer validation, idempotency and post-creation association logic. Missing or unverified capability remains disabled.

After any provider outcome (verified open, invalid result or exception), a freshly sampled clock and current session/account/expiry gate protect the returned attempt. Verified open attachment still commits durably; its final SELECT is guarded in the same batch. Invalid/exceptional outcomes read the current attempt only through that guard. Revoked callers receive no attempt data. Revocation after a committed reservation does not retroactively cancel provider creation; future account deletion must block on that now-active attempt. Unknown creation remains unresolved, not reopened by time. Production must use the fenced entry point and must not expose the trusted helper as an alternate request path. Existing subscription/client authentication is unchanged. Normal clients already use first-party sessions; legacy ID-token fallback must complete session exchange before a future top-up request rather than bypass this guard.

Dependencies: independent session-copy race fix #297, atomic unresolved-attempt deletion guard, terminal financial deletion/replay preservation, route/recovery orchestration, owner merge/configuration/deployment and approved publication gates. Fresh provider sign-in remains possible; this is not permanent account blocking. No account-generation tombstone or session reference is added to purchases/attempts.
