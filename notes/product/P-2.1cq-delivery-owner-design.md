# P-2.1cq Private Follow delivery owner design

Proposed November 12, 2026. Design only, needs-bruce. No schema, implementation, schedule, provider call or production setting is changed. No new user-visible words are proposed. This addresses the owner boundary of [#560](https://github.com/bpmcginley/InternshipFinder/pull/560), not permission to send email.

## Existing guarantees and measured gap

The audit used main `e99a56fdc781c05b7c80be898a1131f45059c51e` and exact #560 `40f07518333e8d40615f6a644552c16202a664bc`. Its runtime, transport, dispatch, claim and budget sources are unchanged on this note's base, `7b7c16179ca17cba8128be21407d5eaab9947840`.

| Source at the audited revision | What it supplies |
| --- | --- |
| `worker/src/follow-confirmation-claim.js:79` and `follow-management-claim.js:85` | Atomic one-job claims and budget debit. A lost claim acknowledgement is spent; raw links cannot be reconstructed for retry. Different jobs remain independently claimable. |
| `worker/src/follow-send-budget.js:11` and migration `0016_follow_send_budget.sql` | A daily aggregate and monotonic clock fence, with no active owner or continuation. A quota is not mutual exclusion. |
| `worker/src/follow-outbox.js:73` and `:278` | Digest-only leases. Expiry can mark an attempt uncertain and release its lease; it cannot establish that a provider handoff stopped and does not cover confirmation/management jobs. |
| `worker/src/follow-link-runtime.js:84` and `:156` | Instance-local busy and held flags. The uncertainty hold survives a late response only in that instance. |
| `worker/src/follow-link-dispatch.js:49` and `:179` | Caller-owned per-kind cursor and next turn, including a capacity-blocked turn. No persistence. |
| `worker/src/follow-email-transport.js:113` | A bounded acknowledgement wait, with no provider AbortSignal contract. Timeout is not cancellation or proof of non-delivery. |

Three additional synthetic probes used the exact runtime, actual claim/dispatch SQL and the existing Node SQLite D1 adapter. Only fake recipients, injected bindings and an in-memory database were used; global fetch was denied. The eight existing runtime scenarios also passed.

| Probe | Measured outcome |
| --- | --- |
| Two independently constructed runtimes share one DB; hold the first binding promise while starting the second on another job. | Two simultaneous handoffs, two correctly charged budget attempts. Per-job safety did not provide global serialization. |
| Reject the first acknowledgement as ambiguous; run the same instance, then construct a fresh instance over the same DB. | The original instance returned held; the new instance processed a different job. The original job stayed claimed. |
| Run one candidate, retain the returned management turn only in test memory, then restart without passing it. | Confirmation was selected twice instead of alternating to management. Durable claims still excluded the first job. |

These are measured JavaScript/SQLite results, not native Workerd multi-isolate, process-crash, provider-delivery or production proofs. They do not demonstrate duplicate sends of the same claimed job. Native two-owner and restart qualification is required for any implementation.

## Minimum proposed private record

Use one dedicated D1 control record for the Follow email lane, separate from the attempt budget and all subscriber outboxes. Initial users are confirmation and management delivery. Any future digest sender must join the same authority before it can use the shared Follow transport. Order mail and other products are outside this lane.

The proposed bounded record contains a format version, a unique acquisition generation, a phase (`ready`, `running` or `held`), and exactly the dispatch continuation: up to two nullable pairs of outbox job ID and expiry, plus the confirmation/management next turn. The generation is concurrency bookkeeping, not a credential or recipient identifier. No email address, subscriber/account ID, scope, raw link/token, rendered message, provider message ID, delivery log or copied payload is added. There is one current record, not an accumulating history. Job IDs can still refer to personal records while those records exist, so this is explicitly new private persistence requiring approval.

This is a proposed shape, not DDL. The existing budget row and digest leases must not be repurposed. No database service identifier, binding value or production limit is selected here.

## Acquisition, continuation and conservative recovery

1. A conditional atomic write acquires only the exact ready record and establishes a fresh generation as running. An ambiguous acknowledgement grants no authority to invoke the runtime. All other instances stay closed. Acquire before invoking #560, preserving the delivery helpers' existing final consent/expiry check followed immediately by synchronous transport. Do not insert an awaited owner write after that final check.
2. Invoke one explicitly bounded runtime pass under that ownership. Keep its existing per-job claims, budget, policy checks and transport unchanged. A proposed implementation must prove that each eligible entry path uses the owner; an owner record alone cannot serialize a bypassing caller.
3. A same-generation conditional completion saves only a strictly validated returned continuation. Missing dispatch output grants no cursor advance. A clean processed or capacity-paused result may atomically save progress and return to ready. A sending-off maintenance result must not clear a pre-existing hold or invent progress. A stale completion cannot release a replacement generation.
4. Any uncertain handoff, unexplained completion or ambiguous owner update remains held, or remains running and is treated as held on restart. Do not automatically reclaim based on elapsed time, an expired link, queue cleanup, a daily budget reset, process restart or a late provider result. The provider can accept a message before its acknowledgement is lost. Recreating #560 is not recovery, and the same spent job must never be retried.
5. Releasing a hold requires an explicitly approved reconciliation procedure establishing both that the old invocation cannot resume and that its unresolved external handoff is settled or incapable of later delivery. Changing a generation only fences future database writes; it does not cancel an old provider request or prevent an old process from making a later handoff. This evidence and reset procedure do not exist yet. If they cannot be established, sending stays off. Do not infer safe recovery from a timeout or an operator's wish to resume.

The smallest next implementation would therefore be a dormant owner/continuation boundary and offline tests. A production scheduler, automatic recovery or provider reconciliation adapter is a separate package. No exactly-once delivery claim is made.

## Persistence and decisions for Bruce

Approval would cover **new private scheduler bookkeeping** and **availability lost in exchange for conservative uncertainty handling**, not new email copy, recipients or sending permission. The proposed persistence policy is:

- Keep the control fence while the lane is configured or an execution/hold remains unresolved. There is no automatic hold expiry. This can stop all Follow link delivery indefinitely after a crash, including one before any send.
- Keep at most two cursor job references, only while useful under the existing queue expiry/deletion rules. A reviewed cleanup must clear obsolete references without clearing ownership or a hold. It must not extend outbox/token retention or recreate a deleted subscriber/job.
- Decommissioning must disable all entry paths and establish quiescence before removing the control record. Restore/rollback must not resurrect a ready state that predates an unresolved handoff. Merely restoring an older D1 backup is not safe recovery.

**Not decided by available evidence:** exact cleanup timing for cursor references, backup/restore retention and protection of the control fence, the verifiable evidence that permits a held generation to be released, who may authorize that release, or a safe response when the provider cannot resolve an ambiguous handoff. These require explicit owner decisions and a reviewed runbook before storage implementation or activation. Approval of the record concept alone does not fill these gaps. No finite hold timeout or automatic retry is proposed.

Production also still needs verified EMAIL/sender configuration, approved postal/presentation values and public action endpoints, recipient entitlement, explicit quota/order reserve, a separately reviewed cadence and per-invocation budget, and qualified retention maintenance. Existing clock/financial cron branches are not an implicit delivery budget. No production values or defaults are proposed here.

## Acceptance before any mount

Use the actual local Workers/D1 runtime to prove two owners cannot reach two handoffs, same-job claims remain spent, and restarts preserve both cursors and a capacity-blocked turn. Inject crashes/lost acknowledgements before acquisition, after claim, during provider acceptance and after provider acknowledgement but before owner completion. Confirm no timer, restart, cleanup, day rollover or late callback releases uncertainty. Verify generation fencing, malformed stored state, deletion/expiry reference cleanup, and restore/decommission behavior against the approved policy. All provider traffic remains synthetic until separately authorized qualification. Existing eight scenarios and three SQLite probes are a starting point, not acceptance of this unimplemented design.
