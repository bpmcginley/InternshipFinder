# P-2.1az Follow writer deadline qualification

This test-only package stacks on exact #488 `a444547f`. The existing Ubuntu 24.04 Tests job exercises the real `scripts/ingest_data_writer.py publish` command against a disposable bare Git origin with file transport only. Windows skips the two cases because its Git Bash timeout cannot qualify Linux process groups.

The fixture runs GNU `timeout --signal=KILL 4s` in default process-group mode. A real receive hook ignores TERM and stays held at either `pre-receive` or `post-receive`. The fixture verifies that the hook joined the timeout group and stopped, then opens the gate that would let a surviving hook write a late marker. The pre-receive deadline leaves the predecessor ref in place. The post-receive deadline leaves the candidate already committed, while the publisher is still waiting for Git to return. A fresh file-transport read verifies the exact tip and public tree in both cases, with one hook entry and no second push.

Python's direct subprocess reports a negative SIGKILL status. A shell represents that signal as 137. The signal status alone cannot tell whether Git published. Pages follows completed ingest runs, including failures. Recovery must read the exact Git ref independently and resolve any Follow checkpoint separately. The Linux fixture qualifies this foreground process group and its Git descendants. [GNU timeout process-group implementation](https://github.com/coreutils/coreutils/blob/v9.4/src/timeout.c) · [Git receive hook ordering](https://git-scm.com/docs/githooks)

The existing #488 coordinator suite complements this process proof with synthetic staged checkpoint and cold recovery checks, including an interrupted process after a committed push. This test does not add a production wrapper, select a timeout duration or qualify provider-side cancellation, private storage, retention, restore or witness behavior.

Across nine successful writer runs, ingest through publication ranged from 1,967 to 2,431 seconds. The longest completed that span in 40m 31s and used 41m 01s of the current 45m job limit. A 40m production deadline would have cut off that successful run. Production integration needs margin for the actual ingest duration, setup and recovery. [Longest observed successful run](https://github.com/bpmcginley/InternshipFinder/actions/runs/43087992793)

This draft adds no workflow, runtime, configuration, public output or provider action. G3 and coordinated writer release remain separate.
