# P-2.1dh bounded unconfirmed scope and orphan retention

Claim on exact `c5e10d60`. Draft needs-bruce. No schema, scheduler, configuration, sending or production changes.

Own new `worker/src/follow-subscriber-expiry-page.js`, shared `worker/test-support/follow-subscriber-expiry-page.js`, new `worker/test-workers/follow-subscriber-expiry-page.test.js` for 0029 qualification, one export in existing `test-support/follow-retention.js`, and this note. Reuse frozen #609 receipt helpers without editing them.

Scope removal preserves seven-day unconfirmed eligibility and waits for matching confirmation-token drainage. Orphan cleanup examines one subscriber and bounds token/digest child deletion with indexed selection and current no-scope guards before root deletion. Daily markers and held/running owner generation are preserved; existing exact cursor redaction remains. Unknown acknowledgement returns no retry or cursor. The existing bulk helper and its callers are unchanged.

## Dormant caller contract

- `expireFollowUnconfirmedPage(db, { enabled: true, maxRows, cursor })`: `maxRows` is an integer from 1 through 128. The existing bounded token pass runs first. A scope is removed only when unconfirmed, created at least seven days before database UTC, and no matching confirmation token remains. A confirmed scope is never selected for deletion, avoiding the confirmed-scope digest cancellation fanout.
- `expireFollowOrphanPage(db, { enabled: true, maxRows: 1, maxChildren, cursor })`: `maxChildren` is an integer from 1 through 128 **per child table**. The candidate is eligible only while it has no scopes. Bounded token and digest prefixes are deleted before the root. Every mutation independently rechecks scope absence. Root deletion additionally requires no token or digest children. No expiry is added to the existing orphan criterion. A live unsubscribe token or attempting digest does not keep a scope-free subscriber indefinitely.
- Both helpers return `disabled` unless `enabled === true`. A successful result has `status: "maintained"`, `examined`, `removed`, `complete` and `next`. Orphan results additionally contain `tokensRemoved`, `digestsRemoved` and `draining`. Counts are direct SQL mutations, checked against explicit successful D1 receipts and bounded cascade changes.
- A cursor is `{ kind, after, through }`, using signed int64 decimal strings and kind `unconfirmed` or `orphans`. `through` is the initial rowid ceiling. The orphan cursor may have `after: null` while the first candidate is still draining. Keep cursors ephemeral and database-local. They are not portable identities or durable state.
- `complete` means scan completion through that pass's ceiling. It does not certify that every due scope was removed. Matching confirmation tokens can block a stale scope, which must be revisited after token drainage and an explicit scan reset. No blocked-scope count is returned.
- While draining, the returned cursor stays immediately **before** the candidate. If that candidate disappears before the next call, the next row remains eligible for examination. If a scope appears, the new current scope guard protects its subscriber and children, and a later successful call can advance past it. Reset to `cursor: null` after each completed pass to see appended rows and reused or inserted rowids behind the earlier cursor. Do not infer an automatic continuation after an unknown acknowledgement.

Each page, eligibility receipt and mutation is in one D1 batch: four statements for scopes, nine for orphans. The first page captures its ceiling and bounded aggregate count/last key in that same transaction. Later pages preserve that explicit pass-start cut. SQL aggregates avoid trusting a separate per-row cursor list. Receipt descriptors are copied once through #609's helpers. No raw subscriber identifiers or retained payloads are returned.

## Bounded work and ownership

Scope deletion cascades to at most one progress row and one confirmation job, plus at most one exact owner-reference redaction. Orphan token deletion may cascade to its unique request-deletion capability. Orphan digest deletion may cascade to its unique pending-progress row. Once those arbitrary child sets are empty, root deletion has at most its unique management job and exact owner-reference redaction. No phase, generation, turn, budget or daily marker is reset. Mismatched owner expiry references remain unchanged.

Native `EXPLAIN QUERY PLAN` verifies rowid seeks and the existing covering child indexes `follow_tokens_subscriber` and `sqlite_autoindex_follow_digest_outbox_2`. Scope/token correlation and no-scope guards use existing composite subscriber indexes. No temporary sort or global unrelated-row scan is required. Outer mutations use `NOT INDEXED` to keep the selected rowid access path.

Measured local workerd/D1 results on the unchanged 0031 schema:

The maximum-child fixture took 65 ms for two calls, including final root removal. These are local measurements, not production latency guarantees. Existing digest writers bound payload bytes and the schema bounds pending progress at 32,768 bytes. The new helper does not parse pending advances or finalize progress during orphan deletion. Arbitrary malformed legacy storage still requires operational qualification. D1 invocation capacity and cadence must be qualified separately before mounting.

## Qualification and remaining boundaries

Twelve new shared scenarios pass in Node's SQLite and actual local D1 through both ordered 0029 and 0031. They cover exact seven-day inclusion, token-before-scope ordering, live claimed/attempting state, every cascade, matching and mismatching owner references, resubscription between guarded statements, removed candidates, signed rowid extremes, reused/appended keys and explicit reset. Sparse/accessor/unstable receipts, rollback after an earlier child delete, and committed-but-lost acknowledgement fail closed without retry. Foreign-key checks find no dangling dependent rows.

The focused adjacent qualification passes 92 strict Node cases and 97 native cases, including existing retention, owner, confirmation outbox, digest outbox and finalization behavior. Scope, formatting and lint checks pass. No dependency install or remote binding was used.

This completes two bounded storage maintenance operations. Existing digest expiry/daily-marker passes, confirmation/token expiry and management expiry remain separate. There is no scheduler mount, lifecycle reset, restore approval, provider operation, new retention criterion, schema change or production activation in this package. A future caller must select work limits, run and resume each pass, reset completed scans, and preserve the independent held/running ownership contract.
