# P-2.2be offline native top-up sales flow

This test-only package qualifies the existing Worker routes together on exact main `c4056b78e39f4598f3a319df2c7ee5dc29c4b127`. It adds one native Workers test file and this note. Runtime, configuration, migrations, registry and shared tracker files are unchanged.

Two scenarios use one synthetic session and local D1 database each. The real `/ai` route consumes the included allowance and rejects another new run. The dashboard configuration, verified offer and Checkout routes then create one attached checkout. Opening and reopening checkout grant no runs. An invalid signature makes no provider request or ledger change. A verified signed delivery grants once, and repeating its receipt makes no further provider read. The second scenario settles through attached recovery with sales disabled before receiving the signed event. Both orders produce one purchase.

A fresh `/me` reports the purchased balance. The real funded `/ai` route consumes one purchased unit, returns the synthetic response, and records purchase funding. A sibling call in the same run does not consume a second unit. Disabling sales removes the hint and blocks new Checkout while preserving the purchased balance and existing recovery behavior.

A third scenario checks ten incomplete payment or funded settings through the actual configuration, offer and Checkout routes. All produce zero synthetic provider calls, checkout reservations and purchases. The complete test settings include an explicit fake signing key and `STRIPE_TOPUP_MODE: "test"` for the separate mode/signing correction. This base does not enforce that new mode setting. These tests do not qualify a real Stripe account, mode, signing endpoint or credentials.

The test reuses exported `attempt`, `price`, `session`, `reply` and fake environment fixtures from `test-support/topup-stripe.js`, plus the actual session and webhook-signature helpers. Every provider response is injected. No network fetch, actual payment, paid AI call or real account is used. No purchase is seeded directly into the ledger. Only local fixture state is reset between scenarios.

Qualification passed all three new native scenarios with migrations limited to 0001 through 0029. Separate runs of the existing checkout route, signed webhook, attached recovery, purchased allowance and AI lifecycle suites passed 65 native cases. Scoped ESLint, Prettier and diff checks passed. Dependencies were reused from an identical Worker lockfile.

From `worker/` with the pinned dependencies and Node 22:

```powershell
$env:CLOUDFLARE_CF_FETCH_ENABLED='false'
$env:WRANGLER_SEND_METRICS='false'
node --unhandled-rejections=strict node_modules/vitest/vitest.mjs run --maxWorkers=1 test-workers/topup-sales-flow.test.js
node --unhandled-rejections=strict node_modules/vitest/vitest.mjs run --maxWorkers=1 test-workers/topup-checkout-route.test.js test-workers/topup-webhook.test.js test-workers/topup-attempt-recovery.test.js test-workers/purchased-allowance.test.js test-workers/ai-lifecycle.test.js
```

The fixture uses JSON AI responses. Existing streaming qualification remains separate. This is backend route composition, not a browser, provider-delivery or deployment rehearsal. Historical completeness and erasure remain outside the sales-flow proof. The package remains needs-bruce and changes no production settings.
