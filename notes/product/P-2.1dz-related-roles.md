# P-2.1dz verified snapshot related roles

Dormant pure helper on main `ebc249cfee7763217533e0745737c48f2b5fc2fc`. Only five new paths are authored, the helper, shared focused cases, tiny Node/native wrappers and this note. The Product lead owns shared Waiting for Bruce tracking. No caller, database, transport, owner, scheduler, configuration, public copy or production defaults change.

`selectFollowRelatedRoles(roles, direct, limits)` consumes trusted already-verified eligible open snapshot facts. Its caller must establish canonical catalog membership, digest, complete window and freshness before calling. `direct` contains the actual deduplicated objects from that same snapshot. Foreign, copied or duplicate direct objects fail as a whole. This helper does not parse JSON or establish provenance. Defensive shape checks preserve the existing snapshot role shape, timestamp form, text lengths and maximum 64 field/state keys. Returned roles are the original public objects, not new retained records.

A candidate must share a company key or at least one canonical field with a direct match. Shared state alone is insufficient. Each candidate uses its best single-seed tuple, ordered by shared employer, count of shared fields and count of shared states. It then sorts by first_seen descending and ASCII role ID ascending. Scores are never pooled across seeds. At most two roles survive. IDs and normalized posting origin/path/query match the renderer's identity boundary. Fragments do not distinguish postings, while queries do. A higher-ranked duplicate posting replaces its lower-ranked representative. No randomization or clock is used.

All five positive safe-integer bounds are explicit caller inputs. `maxRoles` and `maxDirect` bound arrays. `maxPairs` rejects a role-by-direct product before reading role facts, using division to avoid multiplication overflow. Each pair performs at most 128 bounded key lookups. `maxInputBytes` counts exact UTF-8 JSON role-array bytes incrementally after per-role shape/string bounds, avoiding a whole-snapshot serialization. `maxResultBytes` bounds the final two-role result and fails without a partial selection. The helper holds at most two ranked candidates, with bounded fact/index storage. These are technical limits, not a newly selected production policy.

Current `prepareLeasedFollowDigest` exposes only `matched.roles`, and `matchFollowSnapshot` parses the verified pool internally. A future coordinated preparation seam must retain the verified pool and actual renderer-deduplicated direct objects from that same parse. This draft changes neither function and does not silently reparse bytes or accept unverified candidates. It is independent of the separately held public matching/share page design #634.
