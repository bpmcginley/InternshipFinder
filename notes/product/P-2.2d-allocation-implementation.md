Claim: new allocation module, migration 0006/equivalent legacy schema, focused shared Node/local-D1 scenarios and test registration/equivalence, this note and own status row. Preserve all parent files and migrations 0001-0005.

Allocation storage: existing user hash/month/task/run identity, exact purchase hash and allocated/restored/revoked state; one unit implicit. Purchase deletion cascades allocations. No foreign key to monthly-pruned run rows: the approved purchase retention/deletion schedule governs receipts (positive balance until deletion; otherwise 400 days after zero balance and financial resolution). Retention timestamps, cleanup and account-deletion fences remain deferred; durable purchase fingerprints remain unchanged.

New allocation requires an existing Auto-Apply run and selects the oldest spendable purchase by creation time, breaking ties by payment fingerprint. Active governing hold IDs block spending even when held balance is zero. One D1 batch inserts a unique receipt, debits only on that insert's `changes()`, and reads the result. Replays never debit again. Restoration claims an allocated receipt once, then moves exactly one consumed unit using current committed purchase/claim/hold state: available, held, or revoked after refund/loss/terminal state. SQL conservation remains enforced. Failed writes roll back the receipt and balance together; deleted purchases are never recreated.

**Not admission authorization.** Returned receipts describe storage history, including restored/revoked outcomes. The trusted caller must authenticate the owner and establish actual failure before restoration. Existing `limits.release` can delete a newly admitted public run ID, allowing a legitimate retry with that ID. This slice intentionally refuses to debit a restored receipt again. Production integration needs an internal attempt fence tied to the run lifecycle so a delayed release cannot restore a later retry; no new attempt identifier or client retry behavior is introduced here. Monthly/invite-first priority, service/task caps, refund-before-grant recovery, account deletion and provider association checks remain prerequisites before wiring.
