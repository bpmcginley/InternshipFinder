# P-2.3k Employer posting-key mapping

This design requests approval for the public mapping and its byte budget. The UTC-day cap and the five-minute cache have already been approved. The revised disclosure is in [#273](https://github.com/bpmcginley/InternshipFinder/pull/273).

## Coverage

Use the complete public listing export selected for the site release. Include employer keys for organic listings with a valid posting link, including closed listings that still have an Open posting link under the dashboard's Closed filter. Derive the key with the existing canonical employer function in `backend/internscout/site/source.py`. Deduplicate aliases through the same function used for generated employer pages. Reject a capture with missing shards, conflicting keys for the same listing ID, or keys outside the Worker grammar.

Publish `data/employer-posting-keys.json` as the sorted key array accepted by [the Worker parser](https://github.com/bpmcginley/InternshipFinder/pull/292). Limit the uncompressed response to 256 KiB, with the existing limits of 10,000 keys and 200 UTF-8 bytes per key. A failed or oversized capture cannot publish a partial catalog. The catalog contains only canonical keys derived from the public export. It carries no totals, visitor data, listing IDs or posting URLs.

Put the canonical key on the existing dashboard listing rows, including the first-screen copy, and on the direct organic posting links generated for the same release. The dashboard can read the key from its existing listing response. Exclude sponsored boxes, saved-only fallback copies, widgets, email, the extension and Auto-Apply buttons. A role in a sponsored box can still count when someone opens it from an ordinary organic listing. Keep the existing button text and `nocount` behavior. The per-company browser event contains only `employer_posting_open` and the canonical key.

## Offline evidence

I used the exact public data commit `e66294c55f9e5cce25517191ead1866ca64f9d05` selected by [Pages run 42972977656](https://github.com/bpmcginley/InternshipFinder/actions/runs/42972977656). Across its 68 indexed shards, the complete projection found 2,777 keys and zero conflicts between occurrences of the same listing ID. The open-only subset had 2,159 keys. All 12 first-screen rows mapped to keys. The largest key took 70 UTF-8 bytes.

The compact key array was 43,130 bytes and 16,211 bytes under local gzip level 6. The exact Worker at `14ae78492cec4c1098c199ae568eb791f735091a` accepted all 2,777 keys through one synthetic response and rejected an unknown key and a response one byte over its limit. Adding an `employer_key` field in memory increased the first-screen payload from 1,846 to 1,906 gzip bytes. The combined gzip increase across 68 separate shard payloads was 128,986 bytes. These are local serialization measurements.
