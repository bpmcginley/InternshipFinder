# P-2.2ar dormant coverage epoch foundation

Draft [#553](https://github.com/bpmcginley/InternshipFinder/pull/553) stacks on #548 `abd7f9ad` for migration 0030 after 0029. It implements only current coverage metadata fencing under Bruce's approved [#530 design](https://github.com/bpmcginley/InternshipFinder/pull/530), exact `48be283b`. No provider schema is selected and no replay interval is declared complete.

## Stored boundary

One private row per trusted test/live mode contains the opaque random epoch, bounded schema tag, UTC start and nullable covered-through bounds, monotonically increasing revision and health. There are no account, purchase or provider-reference fields. Rotation replaces that row and does not retain an epoch history. Purchase enrollment remains absent.

The schema represents unproven, closed and qualified health so a later independently reviewed authoritative replay transaction can use the approved same record. This module has no operation that writes qualified health or a completed coverage bound. Qualified rows appear only as explicitly synthetic fixtures to verify safe closure and stale-cutoff rejection.

## Operations

All three APIs require literal `enabled: true`. `captureTopupCoverage` returns an exact typed current tuple, or missing/unavailable. A caller must capture before authoritative work. `rotateTopupCoverage` compares the complete expected tuple, creates a fresh random epoch with database UTC start, clears covered-through and sets unproven. A missing-row initialization uses revision 1. Every subsequent rotation continues the mode's revision rather than resetting it.

`closeTopupCoverage` compares the exact current tuple, increments its revision and sets closed. Existing bounds are preserved as metadata, not accepted as current coverage. Every mutation and its guarded readback share one D1 batch. Only its successful write may return the new tuple. Stale capture, concurrent loser and a changed schema/epoch/bound/health cannot overwrite a newer state. Maximum safe-integer revision fails closed. Database time earlier than either retained bound prevents mutation and capture release.

Dense typed receipts and the intended successor fields are required. Lost or malformed acknowledgements return generic unavailable with no retry or compensation. A caller must independently recapture and decide later handling. No method changes balances, settlement, deletion, event receipts or retirement eligibility. Account deletion creates no association to this global metadata.

## Qualification and release limits

Shared Node and actual local D1 cases cover initial/concurrent creation, rotations, other-mode preservation, full-tuple CAS, stale and changed-cutoff captures, closed/unproven transitions, future-bound clock rollback, revision exhaustion, real transaction rollback, unknown committed acknowledgements and existing account deletion. Ordered migration and legacy schema equivalence include one new table and no secondary index. Exact final results are recorded in the PR.

These local fences do not establish continuous provider history or detect restoration of an older internally consistent database. Epoch approval/enrollment, complete bounded replay, authoritative schema selection, provider event completeness, restore handling and erasure-time integration remain separate gates. No runtime caller, route, schedule, provider request, configuration, public wording or activation is added. Independent review and owner merge remain pending.
