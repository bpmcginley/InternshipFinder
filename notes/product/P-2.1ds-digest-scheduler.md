# P-2.1ds scheduled digest candidates

This package adopts reviewed #623 only behind the optional exact boolean `digestCandidates` in the existing trusted maintenance JSON policy. Absent or `false` preserves the original digest scan and works on the deployed 0029 schema; only `true` selects the indexed candidate and requires migration 0033. Invalid selector types and duplicate decoded top-level members in candidate-mode policies fail before D1. Escaped legitimate member names remain valid; omitted-selector legacy parsing is unchanged. Missing indexes or an unavailable candidate never fall back to legacy.

Authored scope is only `worker/src/follow-scheduled-maintenance.js`, its existing native test file, and this note. Base is #623 actual merge `ac8e7ff9e44abfc6b3b08b47a98ee7b647b5e361` (reviewed source `485ea3ce267ad04ad41c91634546bd9c17cd25b2`). No schedule, environment, router, migration, production setting or other lane selection changes.

The D1 wrapper counts every actual `.all` and `.batch`, including `.all` after binding. It checks the existing nondecreasing Worker clock immediately after each await before another operation is admitted. Candidate admission reserves at least three remaining calls; legacy still reserves two. An empty candidate uses two actual reads. A mutation uses those two reads plus one batch; an overlapping terminal transition and delete remain two SQL statements in that one batch (four statements, three binding calls total). The existing reviewed candidate preserves ordered finalization and exact mutation fences. It returns no cursor and completes only after an empty scan; the scheduler does not retry uncertain acknowledgements or a third-due-attempt hold. Exhausted call/deadline budget yields `partial`, while an unavailable or ambiguous candidate yields `unavailable`.
