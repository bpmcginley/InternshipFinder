# P-2.2ap Native checkout recovery UI

The dashboard offers **Check or resume checkout** in Account and the allowance panel when the current account has an attached checkout. The [Worker route](https://github.com/bpmcginley/InternshipFinder/pull/472) is deployed with recovery off pending provider configuration.

The action requires an explicit click and shares the checkout lock. It validates a bounded no-store response and the exact Stripe host. An account refresh can overlap recovery within the same session. A sign-in change invalidates the response even if the original token returns. Settled, expired or inactive outcomes refresh the allowance once. If an account deletion overlaps a sign-in change in this tab or another tab, the old response cannot clear the new session's browser data or show a notice for the previous account. The pending-payment refusal preserves browser data and shows the existing Worker guidance.

Validation covered 16 focused recovery tests, 400 site tests and two Python golden tests. The 836-file archive updates index references and the 11 App and seven Core generation paths for three changed native modules.

[Paired browser evidence](screenshots/P-2.2ap/README.md) includes 24 before/after screenshots at 1280/375 in light/dark and actual synthetic UI assertions. No real account, provider, payment or production requests. Recovery transport is 8 seconds and 16 KiB, streamed with fatal UTF-8, absolute clock checks, no-store and exact response URL. Deletion409 classification is 8 seconds and 4 KiB; all409s preserve local values. Existing purchase/offer requests still require200; existing plan/portal supersession remains tested.

The control is hidden when the Worker omits the capability. Recovery is independent of new sales.

Settled never becomes a claim that payment succeeded or runs were granted; only the current authenticated allowance describes the balance.
