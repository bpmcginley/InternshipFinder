# P-2.3q dormant employer maintenance

Draft [#403](https://github.com/bpmcginley/InternshipFinder/pull/403) is based on published Worker source `51ee9e27`. It adds only `worker/src/employer-posting-maintenance.js`, an automatically discovered standalone local Workers test, this note and the product tracker. Existing counter, route, scheduler, Wrangler, migrations and test registries remain unchanged. No caller enables or invokes the helper in production.

`maintainEmployerPostings(db, {enabled, now, maxRows})` returns only a status. It is disabled unless `enabled` is the boolean `true`; the default path does not access D1. A valid Worker UTC date must equal database UTC before the batch, and every mutating statement separately requires that captured date to equal `date('now')`. The finished Worker clock must remain on that date and not regress. This prevents stale or future Worker clocks from authorizing destructive retention writes and prevents an old invocation from bootstrapping a new UTC day.

One transaction deletes at most `maxRows` expired company rows and `maxRows` old cap rows, then may insert one empty current-day cap. The default and hard maximum are 1,000 rows per table, with lower positive integers available for bounded retries. Both ordered selections and outer deletes use the existing primary-key indexes. Counts strictly older than the current UTC date minus 90 days expire; the exact boundary remains. Existing current caps and their consumed amounts never change. Future caps are not removed, and retained same-day counts without their cap never cause reconstruction. Cap initialization waits until the expired-row and old-cap backlog is clear.

Statuses are `disabled`, `ready`, `progress`, `blocked` or `unavailable`. `progress` means bounded cleanup still has a backlog; it does not promise that the scheduler has run or that a particular row was removed. `ready` is the checked database invariant at that operation, not a durable health latch. A later request must still use the existing retention-checked counter. Missing current caps with retained history and future caps are blocked for owner repair or a later valid empty day. SQL errors roll the batch back; malformed result metadata is unavailable. No company identifiers, counts, catalog data or exception details are returned or logged.

Tradeoffs: a backlog can need several scheduled invocations, and intake remains closed until it is clear. There is no unbounded loop or click-triggered cleanup. The later scheduler must run independently of the intake kill switch so disabling collection does not stop retention. This package adds no schedule or configuration, performs no catalog fetch and makes no retention-policy change.

Validation: Node 22.23.4 passed all 722 Worker Node tests. The pinned local workerd 1.20260911.1 passed all 286 Workers tests in 51 files, including 11 new maintenance tests. New cases cover default-off/invalid inputs, stale/future clocks, exact retention boundary, preserved cap after owner deletion, missing/future cap blocking, two-row catch-up batches, transaction rollback/recovery, concurrency, clock regression and rollover, malformed D1 results, and a 2,001-row synthetic backlog with actual DELETE query-plan index checks. The midnight test runs the real SQL in local D1 with only its database-date expression shifted after the first read; it is not a real wall-clock midnight run. Prettier, ESLint and diff checks pass. The Windows ARM host used an existing matching x64 workerd package read-only after the optional native package was absent locally; no dependency versions changed. All fixtures are synthetic and local. Independent review and exact hosted checks remain required.
