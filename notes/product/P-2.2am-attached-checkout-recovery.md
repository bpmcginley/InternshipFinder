# P-2.2am Attached checkout recovery

Draft [#464](https://github.com/bpmcginley/InternshipFinder/pull/464), needs-bruce, on published 73373196. This package adds the internal service for one existing checkout attached to an account. Approved #226 refund and dispute decisions and #294 run accounting stay in their existing services. The #311 recovery contract remains the authority for expiry and first settlement.

The service authenticates an existing session without refreshing it and selects the account's only active attempt. For an attached open attempt, it reads the stored Checkout ID with a bounded authoritative GET. The exact Checkout, payment mode, hosted page type, attempt metadata and account reference must match before resolving the configured historical offer and live or test mode. The existing recovery then captures the revision and independently reads the complete associated Checkout, payment and reversal evidence. It can settle paid evidence or expire definitively expired evidence. Uncertain results leave the attempt pending. Recovery never creates a Checkout, discovers an unattached ID or sweeps historical reversals.

The session is checked before each GET and before returning a terminal status. The first write of each capture, settlement and expiry batch also requires the exact hashed session ID and attempt account to have an unexpired session at the database's UTC execution time. If that check fails, the batch makes no changes. The existing attempt, revision, claim and deletion checks still govern the transaction. Signed webhook recovery uses the existing trusted path without a browser session. Inconclusive session reads or clock errors return pending. Confirmed expiry or revocation returns auth. If the database clock rejects a write while the request clock still considers the session active, recovery returns pending. A single result contains only a coarse status. Settlement may add available, held or revoked units according to the existing financial decision, so the caller must read the current balance separately.

The three provider read phases keep their existing independent ten-second budgets. The Checkout association phase allows one request and 262,144 bytes. Payment evidence allows three requests and 524,288 aggregate bytes. Reversal evidence allows eighteen requests and 1,048,576 aggregate bytes. The resulting upper bounds are 22 GETs and 1,835,008 response bytes. The synthetic successful settlement uses ten GETs. These budgets cover the provider read phases. Database awaits outside those phases do not have a separate operation-wide deadline here.

A future authenticated POST recovery route can pass the existing session token, database, fixed environment, injected provider transport and clock to `recoverAttachedTopup`. Keep that action independent of the current sales capability and price availability. Route authorization, abuse limits and response mapping belong in the API integration. Use `GET /me` for the resulting spendable balance. Refactor owns the API entrypoint. No-ID discovery, broader reversals, retention scheduling and deployment remain separate.

Synthetic Node SQLite and local Workers D1 scenarios cover sales disabled, an inactive historical Price, paid, expired, uncertain, wrong account, invalid token, no attachment, wrong historical Price, mode disagreement session expiry or revocation during provider reads and immediately before each first write, and inconclusive session reads. The same shared scenarios exercise signed webhook callers without a browser session. The shared fixture asserts GET-only transport, exact read counts and resulting attempt and purchase state. No user-visible copy changes.
