# P-2.2am Attached checkout recovery

Draft [#464](https://github.com/bpmcginley/InternshipFinder/pull/464), needs-bruce, on published 73373196. This package adds the internal service for one existing checkout attached to an account. Approved #226 refund and dispute decisions and #294 run accounting stay in their existing services. The #311 recovery contract remains the authority for expiry and first settlement.

The service authenticates an existing session without refreshing it and selects the account's only active attempt. For an attached open attempt, it reads the stored Checkout ID with a bounded authoritative GET. The exact Checkout, payment mode, hosted page type, attempt metadata and account reference must match before resolving the configured historical offer and live or test mode. The existing recovery then captures the revision and independently reads the complete associated Checkout, payment and reversal evidence. It can settle paid evidence or expire definitively expired evidence. Uncertain results leave the attempt pending. Recovery never creates a Checkout, discovers an unattached ID or sweeps historical reversals.

The session is checked again before each GET, before applying the verified outcome and before returning a terminal status. Recovery stops on expired or revoked sessions, including when revocation is observed during provider I/O. The existing transaction fences the attempt tuple, revision, claim and deletion. A financial transition that already committed under verified evidence remains valid if the session is subsequently revoked. A single result contains only a coarse status. Settlement may add available, held or revoked units according to the existing financial decision, so the caller must read the current balance separately.

A future authenticated POST recovery route can pass the existing session token, database, fixed environment, injected provider transport and clock to `recoverAttachedTopup`. Keep that action independent of the current sales capability and price availability. Route authorization, abuse limits and response mapping belong in the API integration. Use `GET /me` for the resulting spendable balance. Refactor owns the API entrypoint. No-ID discovery, broader reversals, retention scheduling and deployment remain separate.

Synthetic Node SQLite and local Workers D1 scenarios cover sales disabled, an inactive historical Price, paid, expired, uncertain, wrong account, invalid token, no attachment, wrong historical Price, mode disagreement and session expiry or revocation during provider reads. The shared fixture asserts GET-only transport, exact read counts and resulting attempt and purchase state. No user-visible copy changes.
