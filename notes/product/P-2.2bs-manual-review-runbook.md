# P-2.2bs Operator runbook for top-up history review

Use this procedure for the approved [manual-review path](P-2.2-observed-stripe-history.md). The
[listing](P-2.2-manual-review-listing.md) finds records for review. The scheduled check refreshes
Stripe payment state. Only the existing guarded retirement operation can erase an eligible
purchase with independently verified history.

## Before opening checkout

- Rehearse with the terminal route, leased storage and scheduled Worker entry in the intended
  release. Check the intended Worker, database, Stripe account and mode in the owner's
  dashboards. Apply the ordered migrations through 0035 before qualifying scheduled checks.
  Enable `TOPUP_MANUAL_REVIEW_ENABLED=1` and `TOPUP_RECONCILIATION_ENABLED=1` in the qualified
  operator environment. Keep checkout paused during qualification.
  [Terminal route](https://github.com/bpmcginley/InternshipFinder/pull/686) ·
  [Leased storage](https://github.com/bpmcginley/InternshipFinder/pull/685) ·
  [Scheduled Worker entry](https://github.com/bpmcginley/InternshipFinder/pull/687)
- On synthetic fixtures, confirm that authorized first and continuation pages return HTTP 200
  with `Cache-Control: no-store`, a disabled route returns 404, a wrong bearer returns 401, and an
  authorized request with a browser Origin returns 403 without CORS authorization. Cover an empty
  page with a continuation and a failed read returning 503.
- Record the agreed schedule, expected full rotation time and latest acceptable observation age
  in restricted operations. Demonstrate a complete rotation under the intended inventory,
  request limits and deadlines. Verify a deliberately missed check stays pending for review
  and can be retried on a later rotation. Follow the
  [sales release checks](P-2.2ai-topup-sales-readiness.md) and publish the approved disclosures
  before opening checkout.

## Read a page from the operator terminal

Use a private PowerShell 7.4 or later session on the operator's machine with transcription, verbose output
and debugging off. Enter the exact HTTPS Worker endpoint verified in the owner's dashboard.
Supply the existing admin credential at the masked prompt. The token stays out of the command
line, environment and shell history. Keep fingerprints, cursors, credentials and Stripe
identifiers out of logs, tickets and the repo.
[PowerShell request authentication](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/invoke-webrequest#-token)

```powershell
$reviewUri = [uri](Read-Host 'Verified HTTPS Worker endpoint')
if (-not $reviewUri.IsAbsoluteUri -or $reviewUri.Scheme -cne 'https' -or
    $reviewUri.AbsolutePath -cne '/admin/topup-review' -or
    $reviewUri.Query -or $reviewUri.Fragment -or $reviewUri.UserInfo) {
    throw 'Enter the verified HTTPS Worker endpoint with the exact review path.'
}
$reviewToken = Read-Host 'Admin token' -AsSecureString

function Get-TopupReviewPage($cursor) {
    $body = ConvertTo-Json -InputObject @($cursor) -Compress
    $options = @{
        Uri = $reviewUri
        Method = 'Post'
        ContentType = 'application/json'
        Authentication = 'Bearer'
        Token = $reviewToken
        MaximumRedirection = 0
        ConnectionTimeoutSeconds = 15
        OperationTimeoutSeconds = 15
        SkipHttpErrorCheck = $true
        Body = $body
    }
    $response = Invoke-WebRequest @options -ErrorAction Stop
    if ($response.StatusCode -ne 200) {
        throw "Top-up review returned HTTP $($response.StatusCode)."
    }
    $result = $response.Content | ConvertFrom-Json -AsHashtable
    if ($result.candidates -isnot [array] -or -not $result.Contains('next') -or
        ($null -ne $result.next -and $result.next -cnotmatch '^[a-f0-9]{64}$')) {
        throw 'Malformed top-up review page.'
    }
    $result
}

$page = Get-TopupReviewPage $null
$page.candidates | Group-Object age,evidence -NoElement
# Inspect only the required candidate in this private terminal.
# Continue when next is present: $page = Get-TopupReviewPage $page.next
```

The first request sends `[null]`. Send `[next]` until a successful page returns `next: null`,
including when a page has zero candidates. Each page scans a bounded slice of the purchase
index and returns zero-balance granted candidates, with a fingerprint, finance revision, age
and evidence status. An error or timeout makes the scan incomplete. Keep the last successful
cursor in memory and resume after resolving the cause. Start a new scan at `[null]` on the next
review. Close the private terminal after review.

| Age | Evidence | Operator action |
| --- | --- | --- |
| `pending` | `payment_pending` | Resolved payment evidence is incomplete. Recheck the recorded purchase state and Stripe. |
| `not_due` | `under_observation` or `history_gap` | The database's 400-day resolved-zero cutoff has not passed. Leave the record in review. |
| `mature` | `history_gap` | The cutoff has passed. Keep the record pending while independent history remains unavailable. |
| `mature` | `verify_history` | Stored coverage warrants verification. Require fresh payment evidence and independent history before considering retirement. |

## Review a record and respond to gaps

1. The terminal endpoint lists candidates. It supplies no action to refresh a specific record
   or authorize retirement. Leave a record pending when a qualified restricted resolver is
   unavailable. A restricted resolver must re-read the exact purchase and capture its current
   finance revision. The existing server helper `readVerifiedTopupPurchase` resolves fresh
   complete Checkout, PaymentIntent, Charge, Refund and Dispute evidence against the historical
   offer and mode. `recoverTopupPurchase` reconciles under that revision. A conflict requires
   fresh reads and a fresh revision. Keep the outcome and evidence reference in restricted
   operations. [Purchase recovery source](../../worker/src/topup-purchase-recovery.js)
2. Check any claimed coverage against the independent provider and restore evidence required by
   the [coverage design](P-2.2bl-trusted-coverage-advance.md). A completed poll, quiet webhook
   stream, the 400-day age, matching current snapshots and operator acknowledgment leave history
   gaps pending. When independent proof is available, submit only through
   `retireResolvedTopup` with fresh evidence and current qualified coverage. Preserve its
   atomic safeguards. Ordinary customer account deletion follows the existing separate path.
   [Guarded retirement source](../../worker/src/topup-retirement.js)
3. Check the Worker log message `top-up reconciliation` for the invocation status. `wrapped`
   confirms a return to the beginning of the index. `complete` reports one completed pass or an
   empty inventory. `held` signals an unacknowledged pass and `partial` signals a budget or
   deadline stop. Verify progress with the private cursor revision and start state against the
   qualified interval. Use bounded point reads of latest observation markers for selected
   purchases, keyed by a bound fingerprint in restricted database access. Check their
   `outcome`, `reserved_at_ms`, `last_completed_at_ms` and `last_gap_at_ms`. An absent marker
   for an expected purchase, stale pending or missed observations, repeated holds or partials
   without progress, or missing expected invocation statuses warrant investigation.
   [Cursor and marker schema](../../worker/migrations/0035_topup_reconciliation_schedule.sql)
4. If review is unavailable, rotation exceeds the qualified window, or the provider, database,
   or restore state is uncertain, pause new checkout by clearing `TOPUPS_ENABLED` through the
   owner release controls. Keep signed historical settlement, reversals and recovery available
   where their configuration is verified. Stop retirement on any unverified coverage or restore
   state. Before resuming, reconcile the incident window against the verified Stripe account
   and the restored or rolled-back database. Verify replay claims and outstanding purchases,
   confirm the review route works and observe a new full rotation. Leave any unverified
   interval pending under the existing history safeguards.

For the cursor check, use the restricted D1 console on the verified database. This read returns
at most two rows without fingerprints or lease values. Compare the intended mode's revision and
start state across invocations, alongside the status log.

```sql
SELECT mode, revision, after_hash = '' AS at_start
FROM topup_reconciliation_cursor
ORDER BY mode;
```
