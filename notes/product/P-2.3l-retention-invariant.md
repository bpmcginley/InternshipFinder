# P-2.3l request-time retention invariant

Draft [#349](https://github.com/bpmcginley/InternshipFinder/pull/349), based on exact #292 `ce6080afa190b30a7014a4f8deca874e9a482ef2`. Dormant and needs-bruce: no route, schedule, migration, public copy, collection or activation changes. Existing caller APIs and their implementation remain unchanged.

`createRetentionCheckedEmployerPostingCounter({db, cache, load, now})` is constructed within the owning request and exposes only `countAdmitted(admission)`. It consumes the existing single-use opaque admission, checks its UTC day and monotonic Worker clock, and revalidates the existing public catalog lease after the await. It does not retain another request's loader or D1 binding. Existing admission budgeting and catalog validation remain in force.

The conditional company increment requires the admitted UTC day to equal SQLite `date('now')` at database execution, an existing current-day total below the approved cap, no company aggregate older than the existing 90-day cutoff, and no past or future day-cap rows. Existing primary-key indexes support these predicates. The company increment and corresponding day-total increment share one atomic D1 batch; either cap can reject without incrementing the other. Exceptions, unsuccessful results or unexpected result shapes return false. Clicks never delete rows, create a cap, or reset an active total. A separate successful scheduler cleanup can establish the state; deleting company counts does not erase the day total. Ambiguous history with a missing cap keeps the existing cleanup bootstrap closed.

This checks **current database state**, not scheduler history. It does not persist a historical failure latch: if a scheduler call fails while the database already satisfies the invariant, a later request can count. That behavior has an explicit regression test and remains an owner/integration consideration if the final contract requires a durable failure record. Scheduled cleanup is still required for idle retention; this path blocks counting when expired data exists but does not itself erase it. It does not prove that a schedule ran or promise immediate idle erasure. Existing disclosure, catalog mapping, owner deletion and activation gates remain separate.
