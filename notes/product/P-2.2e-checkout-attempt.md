## Storage and transitions

Migration 0008 (0007 reserved by #261) and the identical legacy-schema append add `topup_checkout_attempts`: random attempt ID, existing account hash, approved offer version/amount/currency/units, creation timestamp, nullable verified checkout reference and state. The attempt ID also derives a provider idempotency key; it includes no account identifier. No checkout URL, customer, email, card, private price identifier or provider response body is retained. A partial unique index permits one `creating`/`open` row per account; checkout references are unique across attempts. `expired`/`settled` are reserved terminal states for future verified recovery, with no transition API in this slice.

`reserveTopupCheckout` is off unless trusted server capability explicitly enables it, supplies a verified configured offer and injects an adapter. Missing/invalid configuration returns disabled before any database or adapter operation. It snapshots the immutable offer before awaiting work. A transaction inserts the reservation and returns the account's active row. Only its insert winner invokes the adapter, once, with the frozen request and derived idempotency key. Concurrent/replayed calls return that same row, including when the currently configured offer has changed; they never silently replace its offer or invoke creation again.

The adapter returns a verified normalized open-session tuple. The module rechecks attempt/account/offer/amount/currency/units and a checkout-shaped reference before conditionally attaching it. This comparison is not provider authentication. Throws, malformed/mismatched replies, or crash ambiguity leave `creating` blocked indefinitely; attachment failures leave the committed reservation for recovery. No elapsed timer permits another checkout. A late response cannot reopen an already terminal/deleted row. Returned records are internal state, not a checkout URL, payment confirmation or credit grant.

## Required before wiring

The trusted adapter must verify actual configured private price, payment mode, quantity, account/attempt metadata, currency, eligibility and the existing Managed Payments choice. Offer amount here is the configured pre-tax offer amount; final captured payment including tax must be verified separately before grant. Preserve the original offer/version and exact provider parameters for recovery; never rebuild an old idempotent request from changed configuration. No private setup or numeric offer default is introduced.

[Stripe idempotency](https://docs.stripe.com/api/idempotent_requests) can prune keys after at least 24 hours, so this durable barrier outlives provider deduplication. [Checkout session status](https://docs.stripe.com/api/checkout/sessions/object) is separate from payment status. Verified expiry/recovery, complete paid settlement, refund-before-grant and deletion coordination remain separate; no generic complete/cancel helper is exposed. Account deletion must wait for unresolved creation/payment and serialize against reservation before any production wiring. Do not delete a pending attempt merely to unblock another purchase. Future retention/cleanup must follow the approved account-linked record schedule and financial-resolution gate; this slice does not implement cleanup or infer resolution from age. No route, cron, live adapter, capability exposure, terms publication or deployment is enabled.
