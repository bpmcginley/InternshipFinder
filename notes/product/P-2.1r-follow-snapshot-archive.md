# P-2.1r dormant follow snapshot archive

[PR #327](https://github.com/bpmcginley/InternshipFinder/pull/327) is based on exact ready #320 `0a4b05a8`. Needs Bruce. This module only returns and validates byte mappings. It does not publish, read files or mutate subscription progress.

The proposed public layout is `data/follows/index.json` plus `data/follows/<lowercase SHA-256>.json` for every manifest entry. The canonical v1 manifest names the latest digest and lists each retained snapshot's exact generation, digest, byte length, last enqueue boundary and retention deadline. Generation and committed planning high-water timestamps survive pruning the last blob, while the latest pointer becomes null. Extra files, changed bytes, inconsistent references or deadlines, duplicate days and noncanonical manifests fail closed. The archive checks bounded complete envelopes and their public wire shape. The unchanged #320 adapter still establishes source and role eligibility, and the Worker still validates matching semantics.

Accept the first eligible candidate for each UTC generation date. The caller supplies exact aware millisecond time, coverage and snapshot bounds, enqueue age, publication margin, entry count and aggregate byte bounds. There are no production defaults. A snapshot can enqueue before `generated_at + max_enqueue_age`, exclusive. Keep the exact bytes until that boundary plus the existing 48-hour digest lifetime and the explicit publication margin. Later same-day generations cannot replace the pin. A different candidate at the same generation is an error. Invalid or oversized candidates return no plan and leave existing pins intact. Pruning is allowed at or after the exact retention deadline. It never evicts an unexpired entry to make space.

A plan includes the exact base manifest SHA-256. The staged-transition validator checks the actual current archive, requires that base, and replays the only allowed forward plan. Use the same trusted time for both calculations. If the time or the branch base changes before publishing, replan from the current archive. This is a pure check. The eventual writer must compare the actual branch base and use its existing non-forced publication guard. A rollback also needs this validation against the current archive so an older deployment cannot drop still-live pins.

The local enqueue selector returns latest bytes only while fresh and only when the subscriber's aligned effective lower bound is within the proven coverage. A gap, stale snapshot or newer watermark returns no bytes and changes no progress. A complete no-match window may advance only through the existing Worker CAS. Restore missing pins only from identical digest-verified bytes. No automatic gap skip or older-snapshot fallback is proposed.

A candidate policy for review is a three-day coverage window, 24-hour enqueue age and 24-hour publication margin. With the existing 48-hour job lifetime that retains bytes for 96 hours from generation and can require five snapshots around UTC boundaries. The clean seed's three-day 608,451-byte sample would use about 2.90 MiB for five blobs plus the manifest. This is one measured sample and does not establish a production byte or role cap.
