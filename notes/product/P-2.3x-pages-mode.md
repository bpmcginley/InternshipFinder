Own that workflow, new `backend/tests/test_pages_employer_mode.py`, this note and the two owned tracker rows.

The strict repository variable `INTERNSCOUT_EMPLOYER_POSTING_MODE` maps unset/empty or `off` to the existing invocation, `annotations` to `--employer-postings`, and `capture` to both `--employer-postings --employer-posting-capture`. Other values fail before staging with a generic message that does not echo the value. The step environment transports the value into a quoted Bash case; a fixed array appends arguments to the single existing publisher invocation. No shell evaluation or interpolation of repository-variable text into shell source occurs. Selected-data replacement, the staged data path, placement arguments/reporting, link audit, asset stamping, automatic triggers and publication order are unchanged.

The existing same-export publisher must validate and stage the canonical catalog, slim shards and first preview before rendering and capture. Its fail-closed behavior remains the authority: no fallback or continuation after a failed build. Capture still targets only the supported dashboard and organic generated pages; no paid, widget or feed capture is added.

Release remains two-phase. First the owner may select `annotations`, then qualify the actual published catalog and matching annotations. The separate Worker published-catalog descriptor, intake switch and current UTC maintenance readiness must be qualified before the owner selects `capture`. The existing five-minute catalog lifetime means old valid keys can remain cached until expiry; this workflow does not invalidate a running isolate's cache. Pausing Worker intake independently stops acceptance; maintenance remains separate. Returning Pages to `annotations` or `off` changes the next successfully published artifact, not a page already open in a browser. No Worker setting is changed here.
