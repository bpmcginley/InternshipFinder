## Contract and unchanged criteria

`expireFollowDigestPage(db, {enabled:true, maxRows:1, cursor:null})` examines at most one digest job. Every call requires the literal opt-in and exact one-row bound. An optional continuation is the same database-local signed-int64 rowid tuple used by #596, with kind `digest`. It is caller-owned and ephemeral, never retained by this module.

The entry samples actual database UTC once before its mutation batch, as the existing bulk helper does. It applies that same timestamp through both original update bands and seven-day cutoff. The atomic batch captures its rowid ceiling and aggregate candidate count/last key, then executes these unchanged operations in order on the same candidate:

1. Expired `attempting` lease becomes `uncertain`; payload and lease fields are cleared. Existing migration0012 finalization advances only matching captured scope lifetimes before migration0010 erases pending progress.
2. Expired `queued` or `leased` job becomes `cancelled`; payload and lease fields are cleared without watermark advancement.
3. A job created at or before the seven-day cutoff is deleted. This includes an old attempting job whose lease remains live, preserving the existing unconditional age rule without inventing a state transition. Pending metadata cascades with deletion.

Each mutation is followed by its own direct `changes()` receipt. Strict dense descriptor snapshots distinguish direct work from trigger changes, reject contradictory or partial acknowledgements and never reread a validated cursor property. A failure after the first update rolls the batch back, including watermark changes. Lost acknowledgement may mean a commit occurred; the result is unavailable with no retry or certified continuation. A later explicitly restarted pass observes the actual terminal state and does not replay progress.

The existing `expireFollowPage` gains only the `digest-days` kind, using its existing 1-128 examined-row bound and `expires_at<=` actual SQL UTC predicate. The same rowid ceiling, typed receipts and reset semantics apply. Existing confirmation/token behavior and the bulk retention APIs remain unchanged. Four internal receipt validators are reused through one frozen helper export. No budget counter or owner acquisition/reset is introduced.

At completion, reset the pass. After uncertain acknowledgement, do not automatically resume a returned/guessed cursor. A later reset sees inserted/recycled rowids behind a prior cursor and appended rows beyond its captured ceiling. Complete is a bounded-pass result, not a certificate that every row is now unexpired or a production retention deadline was met. Concurrent inserts and later expiry require subsequent qualified passes.

## Measured work and qualification

The native regression uncovered a planner issue before freeze: a bounded rowid `IN` subquery alone allowed the outer queued-state UPDATE to select the global state index. With 20,000 queued jobs, first/continuation calls read 20,014/20,010 rows. Explicit `NOT INDEXED` on each outer digest mutation forces the existing integer-primary-key lookup while retaining rowid seeks. It does not force a table scan. Actual local D1 now reports 17/12 total batch rows read for those first/continuation pages. EXPLAIN confirms bounded integer-primary-key candidate seeks without sorting.

Measured with the unchanged current migrations and synthetic local Workers/D1:

| Case                                                              | Native result                                                                                                              |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 183 valid advances, padded to the exact 32,768-byte pending bound | 1,176,886 reads, 186 writes and 185 changes in finalization; about 1,842 ms for the helper                                 |
| 185 compact unique advances, padded to 32,768 bytes               | 1,202,698 reads, 188 writes and 187 changes in finalization; 1,833 ms statement duration and about 1,848 ms for the helper |
| Other statements in that 185-advance batch                        | 12 total reads and no writes; clock sampling is a separate constant read                                                   |
| 128 examined daily markers, all expired                           | 643 batch reads, 128 writes, about 1 ms reported statement-duration sum                                                    |
| 128-marker page with no deletion                                  | 512 reads and zero writes                                                                                                  |

The packed 185-advance fixture fits the current schema; adding the next record in that encoding exceeds its byte ceiling. Its exact valid matching watermarks advance once, pending data disappears, and held ownership remains byte-identical. The schema's existing 32,768-byte pending bound limits trigger work. The conservative trigger-change ceiling reuses the reasoning already present in `follow-outbox.js`; it is not a claimed production cost estimate.

Cloudflare's [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) document a 30-second SQL query limit, with the same duration limit applying to an entire batch. Individual SQL/parameter limits still apply inside batches. A batch counts as one query against the per-invocation query allowance. This helper makes one clock read plus one eight-statement batch, with tiny fixed SQL and at most three bound parameters per statement. The measured local case fits that wall-clock ceiling, but approximately 1.2 million reads for one finalization is material. Local timing does not establish deployed capacity, plan allowance, throughput, retention-pass completion or production readiness. A separate trigger optimization can improve that cost without changing this package's semantics.
