# P-2.2z purchased generation lifecycle

Dormant [PR #381](https://github.com/bpmcginley/InternshipFinder/pull/381), based on exact #376 `27164801`, implements approved #294 generation lifecycle and #226 reversal precedence. Bruce authorized the lifecycle and qualified lead integration/deployment. This draft remains **needs-bruce** for independent review, hosted CI and coordinated release; no activation is included.

First admission accepts an optional trusted `allowPurchased` boolean, defaulting to false. With explicit opt-in, existing task, deletion, UTC, call and budget guards still apply. Monthly allowance wins, then invite units, then the oldest eligible purchase by creation time/payment fingerprint. Only autofill can use a purchase. The first run, generation, call, generation receipt, purchase debit and accounting reservations commit in one D1 batch. A missing or ambiguous result gives no call identity or provider permission. Admission is not an automatic retry endpoint.

Migration 0018 broadens the funded metadata constraint to include purchase and adds `topup_generation_allocations`: generation plus the existing receipt's user/month/task/public-run/purchase/state facts. The generation is unique; the purchase foreign key cascades on deletion, while there is deliberately no run foreign key. Receipts survive monthly run cleanup under the purchase's existing retention policy; no new retention clock is introduced. The old #254 receipt table and APIs are unchanged. Do not mix the old allocator with this generation-aware writer for the same new run.

The constraint change copies both populated metadata and call tables before dropping the old child and then parent, renames the replacements and recreates the call index. It uses no new trigger, disabled foreign keys or writable-schema operation. Legacy schema definitions match the migrated result, including SQLite's renamed-table quoting. No historical funding is guessed or backfilled. Local rehearsals cover baseline-to-latest and already-populated 0017, even though the reported production baseline remains 0001; production migration execution belongs to the release owner.

Only the final definitive failure of a generation with no accepted response restores its unit. Receipt transition, consumed decrement and the current available/held/revoked destination commit with the original callback accounting and run deletion. Current committed dispute/refund state controls the destination, including an active dispute whose held balance is zero. A successful generation stays consumed. A generation with no accepted response cannot admit a new sibling while held or revoked; an accepted generation can continue under current limits. Already-admitted calls may finish. Existing deletion fences stop callbacks; purchase deletion cascades receipts, and old callbacks cannot affect a replacement generation reusing the same public run ID.

Actual D1 additionally preserves populated 0017 accepted/reserved calls and legacy receipts, verifies foreign keys/cascade and migration replay; full legacy-schema parity passes. Existing admission/callback/sibling suites remain green. Scoped lint, formatting and diff checks pass.

No live limits, routing, provider, policy copy, workflow, public assets or golden changes. Authentication/rate gates, trusted configuration, provider response handling and integrated release rehearsal remain the eventual caller's responsibility. No live provider or remote D1 request was made.
