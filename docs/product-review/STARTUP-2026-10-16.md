# Dashboard startup: October 16, 2026

Source reviewed: `cbfef6171f08ebc4f9c06a41523519b630a120aa`. The historical 15.7-second first-result
observation is not a benchmark of today's deployed site. This pass measured local payload bytes and
verified offline behavior; it did not drive a browser or measure field performance.

## Changes

- Reduce the first-visit preview from 60 complete result rows to 12. This covers the first ten results,
  the email invitation and two more cards. It keeps the same full row shape and newest-first ordering.
  State files still carry every listing and load immediately after the preview as before. Existing
  query, profile, filter, pagination, accessibility and state-loading behavior are unchanged.
- Give both existing font preloads `fetchpriority="low"`. The same licensed self-hosted faces,
  `font-display:swap` and measured fallback metrics remain. This is only a scheduling hint: browsers
  may ignore it or change priorities when a face is needed. No font or layout-change speedup is claimed.

Google's explanation of [Fetch Priority](https://web.dev/articles/fetch-priority) describes the browser
hint and the need to measure its effects. Do not describe the priority change as removing font bytes.

## Reproducible byte measurements

Run `python scripts/startup_budget.py --baseline-ref cbfef617` from the repository root to compare
against the original 60-row export, or omit the ref to measure the working tree. It uses gzip level 9
with `mtime=0` and LF text endings matching the Linux Pages build. It reports the current data timestamp
and asset sizes without changing exported data.
The sample below is from the October 16 export generated at 15:33:45 UTC.

| Resource | Raw bytes | Estimated gzip bytes |
| --- | ---: | ---: |
| Existing 60-row first.json | 58,017 | 9,883 |
| Same first 12 rows | 10,529 | 2,362 |
| Dashboard HTML before this change | 71,419 | 21,608 |
| core.js | 80,121 | 27,856 |
| app.js | 178,860 | 55,723 |
| listings/index.json | 73,183 | 10,002 |
| Plex Sans font | 45,712 | 45,591 |
| Source Serif font | 51,868 | 51,906 |

The preview alone is 81.9% smaller raw and 76.1% smaller gzipped. At an assumed 20 KiB/s, its
gzip transfer-only cost falls from 0.483 to 0.115 seconds. That is an illustrative 0.367-second
transfer saving, not a predicted first-render improvement: latency, CDN compression, competing
downloads, browser scheduling, execution and rendering are excluded. React/CDN dependencies are
also excluded from the asset table, so it is not the total cold-load budget.

The committed first.json is trimmed to its existing first 12 rows and index.first.rows is updated
to match. No full listing data regeneration or state-file changes are included. This makes the
smaller preview available on deploy, and the export code maintains the same budget thereafter.
A corrected normal ingest/export is still required to clean the sibling task's upstream collisions.

## Validation and remaining checks

- `python -m pytest tests/test_first_screen.py tests/test_shards.py -q` from `backend/`: 30 passed.
  The added case proves 24 full state rows remain available when the preview contains only 12,
  that its contents and order match the state file, and that the index advertises the actual preview.
- The initial complete site test run exposed one existing data failure: `the committed first.json is the top
  of the first-visit list`. The checked-in preview includes a duplicate ID that the browser's merged
  state list deduplicates. The sibling listing-quality task owns fresh-versus-carried duplicate-ID
  guards; do not mask this by arbitrarily dropping whichever copy happens to arrive later. Keeping
  the existing top 12 passes all eight first-screen tests, including the committed-state alignment
  check. This is a bounded preview, not a claim that duplicate state rows or aggregate counts are fixed.
- After trimming only that preview and its row metadata, `node --test tests/site/*.test.mjs`: 166 passed.
